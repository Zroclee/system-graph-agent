## 1. 背景与问题

### 1.1 现状

团队在维护一个典型的"多项目系统"：一个业务系统通常由若干独立代码仓/目录组成，例如

```
order-platform/                 ← 这就是一个"系统"（CodeAtlas 的工作范围）
├── web-admin/                  # 前端管理后台（Vue 3 + Vite）
├── web-portal/                 # 前端门户（React + Next.js）
├── service-user/               # 用户服务（Java + Spring Boot）
├── service-order/              # 订单服务（Python + FastAPI）
├── gateway/                    # 网关（Node.js + NestJS）
└── db-scripts/                 # 数据库 DDL / 迁移脚本

other-projects/                 ← 不属于本系统，不应被访问
├── internal-tools/             # 内部工具（与本系统无业务关系）
└── legacy-experiment/          # 历史实验项目
```

这些项目代码分散、语言异构、彼此通过 HTTP / RPC / 消息队列连接，但**没有任何一份材料能完整描述"它们是如何组成一个系统"的**。

### 1.2 痛点

| 编号 | 痛点 | 具体表现 |
| --- | --- | --- |
| P1 | **系统全景缺失** | 新人入职通常需要 2–4 周才能大致说清"哪个页面调用哪个接口、哪个接口读哪张表" |
| P2 | **改动影响面靠猜** | 改一张表的字段，需要靠经验判断影响哪些后端服务、哪些前端页面，漏改即线上事故 |
| P3 | **前后端契约漂移** | 前端写的 `api/order.ts` 与后端 `OrderController` 长期不对齐，联调才发现字段不一致 |
| P4 | **文档必然腐化** | 手工维护的架构图/接口文档，在代码迭代 1–2 个版本后即失效，无人更新 |
| P5 | **AI 编码助手缺乏系统上下文** | 现有 AI 工具只看到单个文件或单个仓，无法回答"这个函数被谁调用、最终落到哪张表" |
| P6 | **大仓梳理成本极高** | 人工梳理一个中等系统的完整链路，通常需要 5–10 人日，且梳理结果不可复用 |
| P7 | **梳理范围失控** | 用一个目录承载多个系统时，梳理极易"顺手"读到无关项目，导致图谱混入不属于本系统的节点，污染整张图 |
| P8 | **重复全量梳理浪费** | 代码每天在小步迭代，但每次重跑都是全量，既耗时又要求人重复确认已确认过的内容 |

### 1.3 为什么现在做

- **技术可行性成熟**：静态解析（AST）+ 大模型语义理解（LLM）的组合，已经能覆盖"结构确定性"与"语义模糊性"两类问题。
- **Agent 上下文工程有解**：采用"分段梳理 + 每段落盘 JSON + 文档确认"的方式，可以绕开单次上下文窗口的限制，实现超大规模代码库的渐进式理解。
- **版本管理提供锚点**：Git 让"这次梳理对应哪版代码""上次之后改了什么"变成可计算的确定性问题，使增量成为可能。
- **价值可量化**：把 P1 的 2–4 周压到半天，把 P2/P3 的判断从"猜"变成"查图谱"。

### 1.4 不做什么（Out of Scope）

| 不做 | 原因 |
| --- | --- |
| 运行时链路追踪（APM） | 本工具是**静态代码理解**，对齐的是"代码里的调用关系"，不是"生产流量的实际调用"；两者互补但不同 |
| 代码质量/安全扫描 | 属于 SAST 领域，与本工具目标正交 |
| 自动修改代码 | v1 只读；生成"改动建议"留到 v2 评估 |
| 运行时动态插桩 | 需要侵入式改造，成本与收益不匹配 |
| 完整 UML 正向/逆向工程 | 本工具目标偏"系统关联关系"，非严格 UML 建模 |
| 跨系统的联邦图谱 | v1 只处理**单个系统**；跨系统依赖以边界节点表示，不展开（v2 议题） |

## 2. 产品定位与目标

### 2.1 产品形态（已确认：CLI + Web 双端）

一款**以 Agent 为核心驱动**的开发者工具，交付为 **CLI + Web 两个形态**：CLI 负责"跑"（圈定、梳理、增量、导出、查询），Web 负责"看"（图谱交互、确认文档审阅、节点修正、版本对比）。两者共享同一份 `.codeatlas/` 产物目录，Web 由 CLI 一键拉起。

```
用户                 Agent 编排层                     产出
─────    ───────────────────────────    ──────────────────────────
圈定系统 →  ① 技术判定  →  ② 项目解构  →  ③ 链路梳理  →  JSON + 文档 + 图谱
                                     ↕
                   每步落盘 / 可确认 / 可断点续跑 / 边界守卫
                                     ↕
                              Git 版本基线 → 增量刷新
```

| 形态 | 职责 | 典型入口 |
| --- | --- | --- |
| **CLI** | 圈定系统、执行梳理、增量刷新、导出、查询、拉起 Web | `codeatlas init` / `scan` / `update` / `export` / `query` / `serve` |
| **Web** | 图谱画布、多维切换、节点详情与溯源、确认文档审阅与修正、版本对比 | `codeatlas serve` → 本地画布 |

**形态边界**：CLI 是唯一的事实源写入方；Web 只读产物 + 回写"人工确认与修正"这一小类数据，避免两端各自维护状态。

### 2.2 目标用户

| 角色 | 核心诉求 | 典型场景 |
| --- | --- | --- |
| **新入职开发者** | 快速理解系统 | 入职第一天，打开图谱看清"我的模块在整个系统里的位置" |
| **后端开发** | 评估改动影响面 | 改 `order` 表结构前，查"谁读写了这张表" |
| **前端开发** | 对齐接口契约 | 实现页面前，查"这个接口后端返回什么、被哪些页面用过" |
| **架构师 / Tech Lead** | 架构治理 | 识别循环依赖、跨层调用、孤儿接口、僵尸表 |
| **测试工程师** | 圈定回归范围 | 改一个模块，自动推导受影响的 E2E 链路 → 生成回归清单 |
| **AI 编码助手 / Agent** | 系统级上下文 | 作为 MCP/工具被其他 Agent 调用，提供"系统图谱"检索能力 |

### 2.3 核心价值主张

1. **不改代码，只读代码** — 零侵入，随时可跑。
2. **图谱可追溯** — 每个节点、每条边都能回溯到源码的 `文件:行号`，杜绝"AI 编的图"。
3. **多维度视图** — 同一份底层数据，按"架构 / 接口 / 数据 / 链路"等维度重组呈现，回答不同问题。
4. **过程可确认** — 梳理过程落盘为 JSON + 人类可读文档，断点续跑，上下文不丢。
5. **技术栈可扩展** — 通过模板库（Template Pack）机制，新增技术栈只需写一份模板声明。
6. **边界可控** — Agent 的工作范围被圈定在一个系统内，代码访问受白名单约束，杜绝"越界读取其他项目导致图谱混乱"。
7. **版本可增量** — 图谱与 Git 提交绑定，按变更内容定向刷新，不必每次全量重跑。

### 2.4 成功指标

| 指标 | 目标值（v1） | 度量方式 |
| --- | --- | --- |
| 技术栈判定准确率 | ≥ 95% | 人工抽检 50 个项目 |
| API 识别召回率 | ≥ 85% | 对比人工梳理基准 |
| 单模块链路梳理耗时 | ≤ 5 min（中等复杂度模块） | 端到端计时 |
| 图谱节点可溯源率 | 100% | 每个节点必须带 `source.file` |
| 首次可用时间（用户视角） | ≤ 30 min（中等规模系统） | 从圈定系统到看到第一张图谱 |
| 存量系统梳理总耗时 | 相比人工缩短 ≥ 80% | 与基线对比 |
| **范围越界次数** | **0** | 审计日志中"成功越界访问"记录应为 0；所有越界尝试均被阻断并留痕 |
| **单次增量耗时** | **≤ 全量梳理的 20%** | 典型小改动（1–5 个文件）下的端到端计时 |
| **增量漏报率** | **≤ 5%** | 人工核对"变更文件应影响的节点"与"系统实际重跑的节点" |

## 3. 核心概念与术语表

| 术语 | 英文 / 标识 | 定义 |
| --- | --- | --- |
| **系统** | System | **本工具的一等边界概念**。由用户显式圈定的一组项目构成的完整业务系统。Agent 的全部工作被限制在该系统内 |
| **系统声明** | `system.json` | 描述"这个系统由哪些项目构成"的声明文件，是整个工具的边界依据与白名单来源 |
| **范围守卫** | Scope Guard | 强制 Agent 只访问系统白名单内代码的机制，含路径阻断、越界告警、外部依赖边界化 |
| **边界节点** | Boundary / `external` | 系统外部的依赖（第三方 API、外系统服务、外部数据库），在图中作为**终止节点**存在，不展开 |
| **版本基线** | Version Baseline | 一次梳理完成时记录的代码版本快照锚点（Git commit / tree hash + 分支 + 脏标记） |
| **变更集** | Change Set | 两次梳理之间发生的代码变更及其推导出的"受影响范围"，是增量更新的输入 |
| **工作空间** | Workspace | 系统在磁盘上的物理落地目录。**一个系统对应一个工作空间**，工作空间是 System 的载体 |
| **项目** | Project | 一个具备独立技术栈特征的代码单元（一个前端应用、一个后端服务、一个共享库） |
| **模块** | Module | 项目内部按业务/功能划分的单元，是**链路梳理的最小工作单元**（如"订单模块"） |
| **层** | Layer | 代码在架构中的分层归属：`ui` / `api` / `controller` / `service` / `repository` / `entity` / `db` / `shared` |
| **节点** | Node | 图谱上的实体，拥有唯一 ID、类型、所属项目/模块/层、源码位置 |
| **边** | Edge | 节点之间的关系，拥有类型、方向、证据（evidence）、置信度（confidence） |
| **维度** | Dimension | 一种图谱的呈现视角，定义了"取哪些节点、取哪些边、怎么布局" |
| **模板包** | Template Pack | 针对某技术栈的"解构说明书"，声明该栈下 API / 组件 / 模块 / 数据访问的识别规则 |
| **证据** | Evidence | 支撑一条边成立的依据，如 `import` 语句、注解、路由字符串、AST 匹配结果 |
| **置信度** | Confidence | `certain`（静态可证）/ `probable`（强推断）/ `speculative`（LLM 弱推断，需人工确认） |
| **检查点** | Checkpoint | 一次可确认的梳理成果，落盘为 JSON + Markdown 双份 |

### 3.1 层级模型

```
System                 ★ 边界层：Agent 的工作范围，越界即阻断
 └── Workspace         （物理目录，与 System 一一对应）
      └── Project      （技术栈判定粒度）
           └── Module  （链路梳理粒度）
                └── Layer（分层归属，用于维度过滤）
                     └── Node / Edge（图谱元素）

System 之外 → Boundary / external 节点（记录关系，不展开内部）
```

### 3.2 两条贯穿全局的主线

本工具的一切设计都挂在两条主线上，理解它们就理解了全部设计取舍：

| 主线 | 要解决的问题 | 核心机制 | 决策准则 |
| --- | --- | --- | --- |
| **边界主线** | Agent 会不会读到不该读的代码？ | 范围守卫（白名单 + 阻断 + 边界节点化） | 先定边界，再读代码 |
| **版本主线** | 每次都要全量重跑吗？ | 版本基线 + Git diff + 影响面推导 | 没有基线就没有增量 |

## 4. 用户旅程与操作流程

### 4.1 七阶段主流程

```
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 0  系统圈定与边界确认（Scope Binding）          ★ 边界宪法      │
│   指定根目录 → 扫描识别候选项目 → 生成项目白名单 → 记录版本基线 →     │
│   用户确认「这就是本系统」→ 写入 system.json（此后不得越界）          │
└──────────────────────────────┬──────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 1  技术栈判定（Tech Profiling）                                 │
│   读取依赖清单/配置文件 → 判定语言·框架·版本·ORM·路由方案·构建工具     │
│   产出 tech-profile.json + 技术栈判定报告（含判定依据与置信度）         │
└──────────────────────────────┬──────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 2  项目解构（Deconstruction，模板驱动）                          │
│   按模板定位 → API 清单 / 组件清单 / 模块清单 / 数据模型清单            │
│   产出 module-index.json + 解构报告                                   │
└──────────────────────────────┬──────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 3  链路梳理（Link Tracing，按模块循环）                          │
│   对每个模块：数据库表 → 实体 → Repository → Service → Controller →   │
│               API → 前端 api client → store → 页面/组件              │
│   产出 link-<module>.json + 模块链路确认文档        ★ 逐模块确认点     │
└──────────────────────────────┬──────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 4  图谱组装（Graph Assembly）                                    │
│   合并全部 JSON → 去重 → 跨项目建边 → 边界一致性校验 → graph.json      │
└──────────────────────────────┬──────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 5  维度化展示（Visualization）                                   │
│   按维度生成子图 → 交互式画布呈现 → 导出（图片 / Mermaid / 报告）       │
└──────────────────────────────┬──────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 6  版本增量刷新（Incremental Refresh，按需循环触发） ★ 增量通道   │
│   Git diff 版本基线 → 变更文件 → 推导受影响节点/模块 → 定向重跑 →      │
│   合并回图谱 → 输出变更影响报告 → 更新版本基线                         │
└─────────────────────────────────────────────────────────────────────┘
```

阶段 0–5 是**首次全量梳理**路径，阶段 6 是**此后每次代码变更的增量**路径。

### 4.2 关键设计原则

| 原则 | 说明 |
| --- | --- |
| **边界先于一切** | 在读取任何代码之前，先确定"哪些代码属于本系统"。边界未确认，不进入任何后续阶段 |
| **越界即阻断** | 任何试图访问白名单外路径的读取请求被拒绝并审计记录，不"顺便看看" |
| **边界外只记录不展开** | 系统外部依赖作为终止节点进入图谱，用于说明"这里出去了"，但不继续追踪其内部 |
| **基线驱动增量** | 每次梳理完成后固化版本基线；下次变更以基线为参照做差集，而非重新扫描全量 |
| **先判定，后解构** | 不对项目技术栈做准确判定，就不进入解构。判定错误会导致后续全盘错误 |
| **模板驱动而非硬编码** | 识别规则放在模板包里，新增技术栈不改核心引擎 |
| **模块即原子单元** | 链路梳理以模块为单位，一个模块一个检查点，避免单次上下文过载 |
| **每步落盘，JSON 为唯一事实源** | Markdown 文档是给人看的"确认稿"，JSON 是给机器用的"事实源"，两者必须一致 |
| **人在环中确认** | 每个阶段产出可被用户确认/修正，修正结果回写 JSON |
| **可断点续跑** | 任何阶段中断，可从最近检查点恢复，不重复消耗 |

### 4.3 用户操作界面（需求描述，非视觉稿）

**CLI 命令面**

codeatlas export -f mermaid|png|html|md
codeatlas query "谁读写了 t_order" # 图谱查询
codeatlas serve                   # 拉起 Web 画布

## 5. 功能需求（EARS）

> 需求描述遵循 EARS 原则，类型标签含义：
> **[U]** Ubiquitous 通用约束 · **[E]** Event-driven 事件驱动 · **[S]** State-driven 状态驱动 · **[O]** Optional 可选 · **[!]** Unwanted 异常处理

### F1 系统圈定与边界管理（Scope Binding & Guard）★ 边界宪法

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-1.1 | [U] | 系统应支持用户指定一个本地或远程的根目录作为工作空间。 |
| FR-1.2 | [E] | **当**用户选定根目录后，系统应扫描目录树，识别候选项目，并输出候选清单供用户确认。 |
| FR-1.3 | [E] | **当**识别候选项目时，系统应自动排除 `node_modules`、`.git`、`dist`、`build`、`target`、`vendor`、`.venv`、`__pycache__` 等无关目录。 |
| FR-1.4 | [E] | **当**目录中存在嵌套项目（如 monorepo）时，系统应识别各子项目边界，并标注父子关系。 |
| FR-1.5 | [E] | **当**用户确认项目清单后，系统应生成 `system.json`，把这份清单固化为**本系统的工作白名单（`scope.include`）**。 |
| FR-1.6 | [U] | 系统应支持通过 `scope.exclude` 追加排除规则，排除规则优先级高于包含规则。 |
| FR-1.7 | [U] | 系统应为每个项目生成稳定的 `projectId`（基于相对路径 + 包名哈希），确保多次运行与跨版本结果可比对。 |
| FR-1.8 | [S] | **在**系统处于"已圈定"状态时，Agent 的**所有**代码读取操作应被范围守卫约束在白名单路径内。 |
| FR-1.9 | [!] | **如果**任一操作试图读取白名单外的路径，**则**系统应拒绝该操作、记录审计日志（时间 / 目标路径 / 触发阶段 / 触发者），并继续执行不依赖该路径的部分。 |
| FR-1.10 | [U] | 系统应在每次运行结束时输出**范围审计摘要**：本次被阻断的越界访问次数与目标路径列表。 |
| FR-1.11 | [E] | **当**代码中引用了系统外的服务、API、数据库时，系统应将其创建为 `external` 类型的**边界节点**，并建立指向它的边，但**不展开其内部结构**。 |
| FR-1.12 | [U] | 边界节点应在图谱中具有显著区分样式，并在详情中说明"该依赖位于本系统之外"。 |
| FR-1.13 | [!] | **如果**用户希望纳入新的项目，**则**必须通过显式的"扩边"操作更新 `system.json`，系统不得隐式纳入。 |
| FR-1.14 | [E] | **当**系统执行"扩边/缩边"操作时，系统应记录边界变更历史，并在报告中标出"因边界变化而新增/失效的图谱部分"。 |
| FR-1.15 | [!] | **如果**工作空间为空或不包含任何可识别项目，**则**系统应中止流程并明确告知可能原因与排查建议。 |
| FR-1.16 | [!] | **如果**单个项目代码量超过阈值（默认 10 万文件），**则**系统应提示用户并建议按项目分批纳入系统。 |
| FR-1.17 | [U] | 系统应保证"同一系统、同一版本"下的梳理结果可复现：范围白名单是唯一决定因素。 |

### F2 技术栈判定（Tech Profiling）

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-2.1 | [E] | **当**系统圈定完成后，系统应对每个项目执行技术栈判定，输出语言、框架、框架版本、运行时版本、构建工具、包管理器、ORM/数据访问方案、路由方案、状态管理方案。 |
| FR-2.2 | [U] | 系统应基于以下证据源进行判定，并按优先级采信：依赖清单文件（`package.json` / `pom.xml` / `build.gradle` / `requirements.txt` / `pyproject.toml` / `go.mod` / `composer.json`）> 配置文件（`vite.config.*` / `application.yml` / `settings.py`）> 目录结构特征 > 源码文件扩展名分布。 |
| FR-2.3 | [U] | 系统应对每一条判定结论附带**判定依据**（命中的文件与字段）与**置信度**。 |
| FR-2.4 | [E] | **当**判定结果为多技术栈混合（如前端目录里既有 Vue 又有 React）时，系统应以子模块为单位分别判定，而非取单一结论。 |
| FR-2.5 | [E] | **当**判定置信度低于阈值（默认 `probable`）时，系统应在报告中高亮该差异，并请求用户确认。 |
| FR-2.6 | [S] | **当**项目处于"已判定"状态时，系统应锁定该结论并在后续解构中复用，避免重复判定。 |
| FR-2.7 | [U] | 系统应支持用户手工覆写判定结果，覆写记录应写入 `tech-profile.json` 的 `overrides` 字段以便审计。 |
| FR-2.8 | [E] | **当**判定完成后，系统应为每个项目匹配一个或多个模板包，并输出"技术栈 → 模板包"的映射关系。 |
| FR-2.9 | [!] | **如果**某项目的技术栈没有匹配到任何模板包，**则**系统应降级到"通用解构模板"（基于文件扩展名与常见约定做弱识别），并在报告中标注为"低精度模式"。 |
| FR-2.10 | [S] | **当**增量刷新检测到依赖清单发生实质性变更（框架 / ORM / 主版本跃迁）时，系统应重新执行技术栈判定并重新匹配模板包。 |

### F3 项目解构（Deconstruction）

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-3.1 | [E] | **当**模板包匹配完成后，系统应按模板包声明的识别规则，对项目执行解构，产出四类清单：**API 清单、组件清单、模块清单、数据模型清单**。 |
| FR-3.2 | [U] | API 清单中每个条目应包含：HTTP 方法、路径、请求参数、响应结构（能解析则解析）、所在文件与行号、所属 Controller/Handler、鉴权装饰。 |
| FR-3.3 | [U] | 组件清单中每个条目应包含：组件名、类型（页面/容器/展示型）、文件路径、props 定义、事件、依赖的 store、发起的 API 调用。 |
| FR-3.4 | [U] | 模块清单中每个条目应包含：模块名、边界（目录或包）、包含的层、入口文件、对外暴露的接口。 |
| FR-3.5 | [U] | 数据模型清单中每个条目应包含：实体/表名、字段列表、类型、主键、外键、索引、对应的 ORM 注解或 DDL 来源。 |
| FR-3.6 | [E] | **当**数据模型来源同时存在 DDL 脚本与 ORM 实体时，系统应以 DDL 为准并标注两者的差异字段。 |
| FR-3.7 | [E] | **当**解构完成后，系统应生成 `module-index.json`，作为阶段 3 的输入索引。 |
| FR-3.8 | [!] | **如果**某个模块无法确定边界（如没有清晰的目录/包划分），**则**系统应按"顶层业务目录"做启发式切分，并标记为"边界待确认"。 |
| FR-3.9 | [S] | **当**用户在解构报告中对清单做出增删改时，系统应将变更合并进 `module-index.json` 并标记 `humanVerified: true`。 |
| FR-3.10 | [U] | 解构产出的每个元素必须携带 `source.file`，且该路径必须落在 `scope.include` 内。 |

### F4 模块链路梳理（Link Tracing）★ 核心

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-4.1 | [E] | **当**进入链路梳理阶段，系统应**逐个模块**推进，每次只处理一个模块，处理完成后落盘再进入下一个。 |
| FR-4.2 | [U] | 单个模块的梳理应沿"**自底向上**"路径执行：数据库表 → 实体/模型 → Repository/Mapper → Service（业务逻辑）→ Controller/Handler → API 端点 → 前端 API 客户端 → 状态管理 → 页面/组件。 |
| FR-4.3 | [U] | 系统应为每条链路记录**调用边**，每条边必须携带：起点 nodeId、终点 nodeId、关系类型、证据（文件:行号）、置信度。 |
| FR-4.4 | [U] | 系统应在链路梳理中识别并标注**业务逻辑语义**（如"下单校验库存"），而不仅仅是代码调用关系。 |
| FR-4.5 | [E] | **当**单个模块梳理完成后，系统应产出 `link-<moduleId>.json` 与对应的**模块链路确认文档**（Markdown），文档需包含：模块概述、表清单、接口清单、前端触点、完整链路图（Mermaid）、待确认问题。 |
| FR-4.6 | [S] | **当**模块处于"已落盘待确认"状态时，系统应暂停推进并等待用户确认或修正。 |
| FR-4.7 | [E] | **当**用户对确认文档做出修正时，系统应将修正回写至 `link-<moduleId>.json`，并同步更新相关边的 `confidence` 与 `humanVerified` 标记。 |
| FR-4.8 | [U] | 系统应维护 `progress.json`，记录每个模块的梳理状态（`pending` / `in_progress` / `dumped` / `confirmed` / `failed`）与最近处理时间。 |
| FR-4.9 | [S] | **当**梳理过程中断后重新启动时，系统应从 `progress.json` 恢复，跳过已完成模块，从最近未确认模块继续。 |
| FR-4.10 | [!] | **如果**某条边无法找到确凿证据（如动态路由拼接、反射调用、字符串拼接的 SQL），**则**系统应保留该边并标记为 `speculative`，同时列入"待人工确认清单"。 |
| FR-4.11 | [!] | **如果**单模块处理过程中上下文用量接近阈值（默认 80%），**则**系统应主动落盘当前进度并提示用户进入下一轮，避免上下文溢出导致信息丢失。 |
| FR-4.12 | [E] | **当**跨项目调用发生时（前端 → 后端、服务 → 服务），系统应通过**接口签名匹配 + 路径匹配 + 语义匹配**三重策略建立跨项目边。 |
| FR-4.13 | [O] | **当**系统中存在消息队列 / 事件总线定义时，系统应梳理发布-订阅关系，形成事件链路。 |
| FR-4.14 | [U] | 链路梳理的每一轮对话都应以"**已确认 JSON + 当前模块源码片段**"作为上下文输入，禁止将全量代码一次性注入。 |
| FR-4.15 | [S] | **在**链路梳理过程中，所有源码读取应受范围守卫约束；跨出系统边界的调用应终止于 `external` 边界节点。 |
| FR-4.16 | [E] | **当**一条链路终止于外部依赖时，系统应显式标注"链路在此离开本系统"及其目标类型（第三方 API / 外系统服务 / 外部数据库）。 |
| FR-4.17 | [U] | 系统应能识别**隐式耦合**（如多个系统共享同一张数据库表）并标记为风险，即使它不体现为一次 API 调用。 |

### F5 JSON 中间产物与文档确认 ★ 防上下文丢失机制

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-5.1 | [U] | 系统应使用 JSON 作为**唯一的机器可读事实源**，所有阶段产物必须落盘到工作空间的 `.codeatlas/` 目录下。 |
| FR-5.2 | [U] | 系统应为每类 JSON 定义并校验 Schema（见第 6 章），不符合 Schema 的产物应被拒绝写入并报错。 |
| FR-5.3 | [E] | **当**任一阶段完成后，系统应同时产出 **JSON（机器）+ Markdown（人类）** 双份产物，两者内容必须一致。 |
| FR-5.4 | [U] | Markdown 确认文档应至少包含：本阶段结论摘要、关键节点表（含 ID / 名称 / 类型 / 源码位置）、关键关系表、置信度分布、**待确认问题清单**。 |
| FR-5.5 | [E] | **当**用户确认一份文档时，系统应在对应 JSON 中写入 `confirmedBy` 与 `confirmedAt`。 |
| FR-5.6 | [S] | **当**后续阶段需要引用前序结论时，系统应**加载 JSON 文件而非依赖对话历史**。 |
| FR-5.7 | [U] | 系统应保证 JSON 产物**幂等可重建**：删除产物后重跑，应能得到结构一致的结果（允许行号等细节差异）。 |
| FR-5.8 | [E] | **当**检测到源码发生变更时，系统应标记受影响的节点与模块为"待刷新"，而非全量重跑。 |
| FR-5.9 | [!] | **如果**两次运行结果出现结构性差异，**则**系统应输出变更 Diff 报告（新增/删除/修改的节点与边），供用户判断。 |
| FR-5.10 | [U] | 所有产物应记录其生成时的 `basedOn`（版本基线 ID）与 `graphVersion`，用于判断"这份图谱对应哪一版代码"。 |
| FR-5.11 | [E] | **当**图谱对应的代码已有更新提交时，系统应在 Web 画布上标注"图谱已过期"并展示落后的提交数。 |

### F6 图谱组装（Graph Assembly）

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-6.1 | [E] | **当**所有模块链路梳理完成后，系统应合并全部 `link-*.json`，去重并生成统一的 `graph.json`。 |
| FR-6.2 | [U] | 每个节点应具备全局唯一 ID，命名规则建议为 `<projectId>:<layer>:<filePathHash>:<name>`。 |
| FR-6.3 | [E] | **当**合并时出现同名节点，系统应按"路径 + 类型"二次判定是同一实体还是不同实体。 |
| FR-6.4 | [U] | 系统应执行图谱完整性校验，至少包括：孤儿节点（无任何边）、断链（边的端点不存在）、循环依赖、跨层反向调用（如 Repository 调用 Controller）。 |
| FR-6.5 | [E] | **当**校验发现问题时，系统应输出"图谱健康度报告"，按严重级别列出问题清单。 |
| FR-6.6 | [E] | **当**图谱组装完成后，系统应生成一张汇总性的"系统总览图"（项目级拓扑）。 |
| FR-6.7 | [U] | 系统应执行**边界一致性校验**：所有节点的 `source.file` 必须落在 `scope.include` 内，发现越界节点即视为缺陷并剔除，同时写入审计日志。 |
| FR-6.8 | [E] | **当**图谱组装完成后，系统应生成图谱版本快照并归档到 `snapshots/`，支持与历史版本做图谱级 diff。 |

### F7 维度化展示与交互

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-7.1 | [U] | 系统应支持按维度生成并切换图谱视图，v1 至少支持第 8 章定义的 D1–D6 维度。 |
| FR-7.2 | [U] | 系统应为每个维度定义独立的**节点类型集合、边类型集合、布局算法与默认过滤条件**。 |
| FR-7.3 | [E] | **当**用户点击任一节点时，右侧面板应展示该节点的完整信息：名称、类型、所属项目/模块/层、源码位置（可跳转编辑器）、业务说明、入边与出边列表。 |
| FR-7.4 | [E] | **当**用户点击任一节点时，系统应高亮其**上下游链路**（可配置跳数，默认 2 跳）。 |
| FR-7.5 | [E] | **当**用户按项目 / 模块 / 层 / 置信度进行过滤时，图谱应实时重绘，并保持已选节点的选中状态。 |
| FR-7.6 | [U] | 系统应支持按关键字搜索节点，并支持按节点 ID 精确定位。 |
| FR-7.7 | [U] | 系统应通过**视觉编码**区分节点属性：形状区分类型、颜色区分项目、边框虚实区分置信度、边线样式区分关系类型。 |
| FR-7.8 | [E] | **当**用户选中一条端到端链路（如"某个页面的下单流程"）时，系统应支持"路径高亮 + 时序展开"两种呈现方式。 |
| FR-7.9 | [E] | **当**用户执行导出时，系统应支持导出为：PNG/SVG 图片、Mermaid 代码、独立 HTML（可离线打开）、Markdown 报告。 |
| FR-7.10 | [O] | **当**图谱规模超过渲染阈值（默认 2000 节点）时，系统应启用聚合模式（按模块折叠为超级节点），并支持逐层下钻。 |
| FR-7.11 | [!] | **如果**某节点缺少源码位置信息，**则**系统应在画布上以显著样式（如虚线 + 警示色）标注为"来源未知"。 |
| FR-7.12 | [U] | 系统应以显著样式区分 `external` 边界节点，并在画布上提供"系统边界"的视觉标示。 |
| FR-7.13 | [E] | **当**用户打开版本对比视图时，系统应列出两个基线之间新增 / 删除 / 变更的节点与边，以及受影响的端到端链路。 |

### F8 版本基线与增量更新（Git-Driven）★ 成本控制核心

#### F8-1 版本基线

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-8.1 | [E] | **当**一次梳理（全量或增量）完成后，系统应固化**版本基线**：每个项目的 `commit`（或 tree hash）、分支、是否有未提交改动（dirty）、记录时间，写入 `system.json` 的 `versionBaseline`。 |
| FR-8.2 | [U] | 版本基线应按系统维度记录，而非仅按单个项目，以支持"整个系统在某一个代码版本上的图谱快照"。 |
| FR-8.3 | [!] | **如果**某个项目不是 Git 仓库（或环境中无 Git），**则**系统应降级为**文件哈希基线**（对项目文件树计算内容哈希），并在报告中标注"该项目的增量精度较低"。 |
| FR-8.4 | [E] | **当**项目存在未提交改动时，系统应在基线中标记 `dirty: true`，并在报告中提示"当前图谱对应的代码含未提交变更"。 |
| FR-8.5 | [U] | 系统应支持以 **tag / 分支 / 任意 commit** 作为基线锚点，而不仅限于 HEAD。 |

#### F8-2 变更检测

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-8.6 | [E] | **当**用户触发增量刷新时，系统应在每个项目执行 `git diff <baselineCommit>..HEAD --name-status`（含 `--find-renames`），得到变更文件列表。 |
| FR-8.7 | [U] | 变更检测应区分变更类型：新增（A）/ 修改（M）/ 删除（D）/ 重命名（R）/ 复制（C），并分别走不同处理分支。 |
| FR-8.8 | [E] | **当**检测到重命名或移动时，系统应依据内容相似度判定为"节点位置变更"而非"删除 + 新增"，保留其历史标识与人工确认状态。 |
| FR-8.9 | [U] | 变更检测还应覆盖**清单类文件**的变更（依赖清单 / 配置文件 / 路由注册文件 / DDL 脚本），因为它们影响的不是自身节点，而是大量下游节点。 |

#### F8-3 影响面推导

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-8.10 | [E] | **当**得到变更文件列表后，系统应将其**映射到受影响的图谱节点**（节点携带 `source.file`，可直接反查）。 |
| FR-8.11 | [E] | **当**确定直接变更节点后，系统应沿图谱边进行**影响扩散**：一跳为"受直接影响"（必须重跑），二跳为"契约可能受影响"（需校验）。 |
| FR-8.12 | [U] | 影响扩散应遵循按边类型区分的规则：`http-call` / `exposes` / `maps-to` / `reads` / `writes` 触发跨项目重校验；`imports` / `calls` 触发同项目重跑。 |
| FR-8.13 | [U] | 系统应计算出**最小重跑集**：受影响模块集合 = 直接变更文件所属模块 ∪ 受影响节点所属模块（去重）。 |
| FR-8.14 | [E] | **当**变更涉及 API 签名（路径 / 方法 / 参数 / 返回结构）时，系统应强制触发**跨项目契约重校验**，即使前端代码未变更。 |
| FR-8.15 | [E] | **当**变更涉及 DDL（建表 / 改字段 / 加索引）时，系统应强制重算该表的 D3 数据访问子图与 D5 数据模型子图，并输出影响面报告。 |
| FR-8.16 | [!] | **如果**变更命中"结构性变更"（新增/删除项目、顶层目录重构、技术栈升级、依赖清单大改），**则**系统应判定最小重跑集失效，提示用户执行全量重跑。 |
| FR-8.17 | [U] | 系统应支持 `--dry-run`：只输出影响面推导结果（哪些模块将被重跑、哪些被跳过），不实际执行梳理。 |

#### F8-4 增量执行与合并

| ID | 类型 | 需求描述 |
| --- | --- | --- |
| FR-8.18 | [E] | **当**最小重跑集确定后，系统应仅对这些模块执行链路梳理，其余模块的既有产物直接复用。 |
| FR-8.19 | [E] | **当**增量梳理完成后，系统应将新产物与旧图谱**合并**：替换受影响模块的节点与边，保留未受影响部分。 |
| FR-8.20 | [U] | 合并时应执行**悬空边清理**：被删除节点上的边必须同步删除，并记录到变更报告中。 |
| FR-8.21 | [E] | **当**合并完成后，系统应输出**变更影响报告** `change-report.md`，包含：变更文件清单、受影响模块、新增/删除/修改的节点与边、受影响的端到端链路、建议的回归范围。 |
| FR-8.22 | [E] | **当**增量完成后，系统应生成新的**图谱版本快照**并归档，同时更新 `system.json` 中的版本基线。 |
| FR-8.23 | [S] | **在**增量模式下，已完成且未受影响的模块的 `confirmed` 状态应被保留，不要求用户重新确认。 |
| FR-8.24 | [!] | **如果**增量梳理过程中发现某模块的实际情况与既有产物冲突（如新增了未记录的接口），**则**系统应将其升级为"需重跑模块"并纳入本轮或下一轮。 |
| FR-8.25 | [O] | **当**用户配置了触发方式时，系统应支持手动（默认）、Git hook、定时任务三种增量触发方式，并推送变更影响报告。 |
| FR-8.26 | [U] | 系统应保证增量结果与全量重跑结果**语义等价**（AC-18 验收），否则视为缺陷。 |

## 7. 技术栈模板库（Template Pack）

### 7.1 模板契约

每个模板包是一个声明式配置文件，描述"在这个技术栈里，去哪里找什么"。

```yaml
# templates/spring-boot/template.yaml
id: spring-boot
displayName: Spring Boot (Java)
match:
  files: [ "pom.xml", "build.gradle" ]
  dependencies: [ "spring-boot-starter-web" ]
  extensions: [ ".java" ]

# 项目结构约定
structure:
  sourceRoots: [ "src/main/java" ]
  resourceRoots: [ "src/main/resources" ]
  moduleDetect: "by-package"          # by-package | by-directory

# 关键元素的识别规则
recognizers:

  endpoint:
    strategy: annotation
    match:
      annotations: [ "@GetMapping", "@PostMapping", "@PutMapping", "@DeleteMapping", "@RequestMapping" ]
    extract:
      method: from-annotation
      path: from-annotation
      params: from-method-signature
      responseType: from-return-type

  controller:
    strategy: annotation
    match:
      annotations: [ "@RestController", "@Controller" ]

  service:
    strategy: annotation
    match:
      annotations: [ "@Service", "@Component" ]

  repository:
    strategy: annotation
    match:
      annotations: [ "@Repository" ]
    interfaces: [ "JpaRepository", "CrudRepository", "MyBatisMapper" ]

  entity:
    strategy: annotation
    match:
      annotations: [ "@Entity", "@Table", "@Document" ]
    mapToTable:
      from: "@Table(name)"  # 缺省时按驼峰转下划线推导

  table:
    strategy: external
    sources: [ "**/*.sql", "src/main/resources/db/migration/**" ]

# 边推断规则
edgeRules:
  - type: exposes
    from: controller
    to: endpoint
    when: "endpoint 定义在 controller 类内部"
  - type: maps-to
    from: entity
    to: table
    when: "entity 的 @Table 名称与 table 名匹配"
  - type: calls
    from: service
    to: repository
    when: "service 中注入了该 repository 字段"

# 增量敏感文件：这些文件变更时应触发更大范围的重校验
incrementalSensitive:
  - "pom.xml"
  - "build.gradle"
  - "src/main/resources/application*.yml"
  - "**/db/migration/**"
```

> `incrementalSensitive` 是 v0.2 新增的模板字段：它告诉增量引擎"这几类文件一改，判定结论本身可能失效"，从而触发范围升级。

### 7.2 模板包清单（v1 规划）

| 类别 | 模板包 | 关键识别目标 |
| --- | --- | --- |
| 前端 | `vue2` / `vue3` | `.vue` SFC、`<script setup>`、router 配置、Pinia/Vuex store、axios 封装 |
| 前端 | `react` | `.tsx/.jsx`、函数组件 Hook、React Router、Redux/Zustand、fetch/axios |
| 前端 | `nextjs` | `app/` 与 `pages/` 路由、Server Actions、API Routes |
| 后端 | `spring-boot` | `@RestController`、`@Service`、`@Entity`、MyBatis Mapper XML |
| 后端 | `python-fastapi` | `@app.get/post`、Pydantic Model、SQLAlchemy Model、Depends 注入 |
| 后端 | `python-django` | `urls.py`、`views`、`models.Model`、serializers |
| 后端 | `python-flask` | `@app.route`、蓝图、SQLAlchemy |
| 后端 | `node-express` | `router.get/post`、middleware、Sequelize/Mongoose Model |
| 后端 | `node-nestjs` | `@Controller`、`@Injectable`、TypeORM/Prisma Entity |
| 后端 | `go-gin` | `router.GET`、GORM Model、handler |
| 数据库 | `sql-ddl` | `CREATE TABLE`、`FOREIGN KEY`、索引 |
| 数据库 | `mybatis-xml` | `<select>/<insert>` 与表名映射 |
| 通用 | `fallback-generic` | 基于扩展名与目录约定的弱识别 |

### 7.3 扩展方式

新增一个技术栈 = 新增一个 `templates/<id>/template.yaml`，无需改动核心引擎。模板包应支持版本号，以便随框架演进更新识别规则。

## 8. 图谱维度定义

> **核心原则**：同一份 `graph.json` 数据，不同维度 = 不同的「节点类型白名单 + 边类型白名单 + 布局算法 + 默认折叠层级」。

### D1 · 项目架构图（Project Architecture）

**回答的问题**：代码是怎么组织的？模块之间怎么依赖？

| 项 | 定义 |
| --- | --- |
| 节点类型 | `project`、`module`、`package`、`controller`、`service`、`repository`、`external` |
| 边类型 | `contains`、`imports`、`extends`/`implements`、`leaves-system` |
| 布局 | 分层有向图（Hierarchical / Dagre），项目为根，层为列 |
| 默认粒度 | 模块级（可下钻到类级） |
| 特色能力 | 循环依赖检测、跨层反向调用高亮、扇入/扇出统计、**系统边界标示** |

### D2 · 前后端调用图（API Interaction）

**回答的问题**：前端调了哪些接口？接口有没有人用？契约是否对齐？

| 项 | 定义 |
| --- | --- |
| 节点类型 | `component`、`store`、`apiClient`、`endpoint`、`external` |
| 边类型 | `http-call`、`uses-store`、`renders`、`leaves-system` |
| 布局 | 双向分组布局（左侧前端、右侧后端，中间接口列，边界节点置于最右） |
| 默认粒度 | 接口级 |
| 特色能力 | **孤儿接口**（无前端调用）、**幽灵调用**（前端调了不存在的接口）、参数/响应结构 diff、**外部接口调用清单** |

### D3 · 后端数据访问图（Data Access）

**回答的问题**：谁读写了哪张表？改表会影响谁？

| 项 | 定义 |
| --- | --- |
| 节点类型 | `service`、`repository`、`entity`、`table`、`external` |
| 边类型 | `calls`、`reads`、`writes`、`maps-to`、`leaves-system` |
| 布局 | 从左到右的数据流向（Service → Repository → Table） |
| 默认粒度 | 表级 |
| 特色能力 | 表影响面分析、读写性质区分（R/W）、无主表（无人访问）识别、**共享表隐式耦合识别** |

### D4 · 端到端链路图（End-to-End Trace）

**回答的问题**：一个业务功能，从点击到落库，完整走了哪些代码？

| 项 | 定义 |
| --- | --- |
| 节点类型 | 全类型，但**按链路裁剪** |
| 边类型 | 全类型，按调用序串联 |
| 布局 | 时序/泳道布局（可切换为路径高亮） |
| 默认粒度 | 单条业务链路 |
| 特色能力 | 链路业务语义标注、断点提示（链路中断处）、**离系统点标注**、回归测试范围推导 |

### D5 · 数据模型图（Data Model / ER）

**回答的问题**：数据表之间是什么关系？

| 项 | 定义 |
| --- | --- |
| 节点类型 | `table`、`column` |
| 边类型 | `fk` |
| 布局 | ER 布局（表为容器，字段为内部节点） |
| 默认粒度 | 表 + 关键字段 |
| 特色能力 | 字段级血缘、孤立表识别、字段命名规范检查 |

### D6 · 模块依赖图（Module Dependency）

**回答的问题**：模块之间耦合程度如何？有没有循环？

| 项 | 定义 |
| --- | --- |
| 节点类型 | `module` |
| 边类型 | 聚合后的 `imports` / `calls`（带权重） |
| 布局 | 力导向图（Force-directed），边宽表示依赖强度 |
| 默认粒度 | 模块 |
| 特色能力 | 强耦合模块对识别、循环依赖环、依赖权重热力 |

### 维度对比速查

| 维度 | 节点类型数 | 边类型 | 布局 | 主要用户 | 典型问题 |
| --- | --- | --- | --- | --- | --- |
| D1 架构 | 7 | 4 | 分层 | 架构师、新人 | 代码怎么组织的 |
| D2 接口 | 5 | 4 | 分组双向 | 前后端开发 | 接口有没有人对齐 |

## 9. 关键技术方案与决策准则

### 9.1 静态解析 vs LLM 推断的分工

这是本工具最核心的技术决策：**能用静态解析拿到确定答案的，绝不交给 LLM 猜**。

| 任务 | 归属 | 理由 |
| --- | --- | --- |
| 依赖清单解析（package.json / pom.xml） | 静态 | 结构化数据，100% 确定 |
| 框架与版本判定 | 静态 | 同上 |
| 文件类型分布统计 | 静态 | 同上 |
| 注解/装饰器识别（`@GetMapping`） | 静态（AST / 语法树） | 语法层面可确定 |
| 函数签名与参数提取 | 静态（AST） | 同上 |
| import / require 依赖图 | 静态（AST） | 同上 |
| SQL 语句中的表名提取 | 静态（正则 + 词法） | 大部分可确定 |
| 前端 HTTP 调用点识别 | 静态（AST） | 可确定调用位置 |
| **边界判定（路径是否在白名单内）** | 静态 | 路径比较，无需推断，必须 100% 准确 |
| **Git 变更检测与影响面推导** | 静态 | 基于 diff 与图遍历，可完全确定 |
| **前端调用 ↔ 后端路由匹配** | 静态优先 + LLM 兜底 | 路径拼接/常量变量多，静态匹配 60–80%，剩余交 LLM |
| **业务语义命名与归类** | LLM | 需要语义理解 |
| **模块边界启发式切分** | LLM + 规则 | 缺乏显式声明时需要语义判断 |
| **动态调用/反射/字符串拼接** | LLM 推断，标记 speculative | 静态不可达 |
| **业务逻辑说明撰写** | LLM | 需要阅读代码并总结 |

**决策准则**：

1. **确定性优先**：凡 AST 能给出的，不调用 LLM。
2. **证据必留**：每条 LLM 推断出的边，必须附上它读过的代码证据。
3. **置信度分层**：`certain` / `probable` / `speculative` 三级必须显式标注，UI 上以视觉区分。
4. **不确定就暴露**：宁可留「待确认」，不要编造一个看起来合理的连接。
5. **成本与规模匹配**：LLM 只用于"静态解析不到的缺口"，把 token 花在刀刃上。

### 9.2 上下文管理策略（防丢失）

| 策略 | 说明 |
| --- | --- |
| **分段处理** | 以模块为原子单位，一次只处理一个模块 |
| **落盘优先** | 每完成一个模块立刻写 JSON + Markdown，再做下一轮 |
| **引用而非内联** | 上下文注入的是 JSON 摘要 + 必要的源码片段，不是全量代码 |
| **检查点确认** | 每模块一个确认点，人审后标记 `confirmed` |
| **进度可恢复** | `progress.json` 支持断点续跑 |
| **版本化产物** | JSON 保存 `schemaVersion` 与 `generatedAt`，避免多轮产物不兼容 |
| **双份一致** | JSON（机器）与 Markdown（人类）必须同步生成、内容一致 |

**决策准则**：**任何未落盘的知识都视为已丢失。**

### 9.3 图谱渲染引擎选型

| 引擎 | 优势 | 劣势 | 建议用途 |
| --- | --- | --- | --- |
| **Mermaid** | 零依赖、可嵌入 Markdown、易导出 | 大图性能差、交互弱 | 文档内静态图、模块链路图 |
| **Graphviz (DOT)** | 自动布局质量高 | 静态、需二进制约 | 架构图导出、CI 产物 |
| **Cytoscape.js** | 图分析能力强、大图性能好、支持布局插件 | 学习曲线陡 | **交互式主画布（推荐）** |
| **React Flow** | 交互定制自由度高、节点可放任意组件 | 大规模图需自行优化 | 定制化交互画布 |
| **ECharts Graph** | 中文生态好、开箱即用、图表能力全面 | 图布局能力一般 | 快速原型、中小规模 |
| **D3** | 最灵活 | 开发成本最高 | 特殊可视化需求 |

**建议方案**：

- **文档层**：Mermaid（链路确认文档、健康度报告内嵌）
- **主画布**：Cytoscape.js（交互、大图、多布局切换）
- **导出层**：Graphviz + SVG（印刷级导出）

**决策准则**：文档内 20 节点以内用 Mermaid，超过 2000 节点必须启用聚合折叠，中间区间用 Cytoscape.js 全量渲染。

### 9.4 跨项目接口匹配策略

前端 `request.get('/api/v1/orders')` 与后端 `@GetMapping("/api/v1/orders")` 如何自动对上？

| 层级 | 策略 | 置信度 |
| --- | --- | --- |
| L1 | **精确路径匹配**（含网关前缀去除、常量展开） | `certain` |
| L2 | **模板路径归一化匹配**（`/orders/{id}` ↔ `/orders/${id}` ↔ `/orders/:id`） | `probable` |
| L3 | **语义匹配**（方法名 / 变量名 / 业务词汇相似度 + LLM 判断） | `probable` |
| L4 | **参数结构匹配**（请求体字段与 DTO 字段重合度） | `probable` |
| L5 | **人工确认** | 用户裁决后置为 `certain` |

**决策准则**：L1+L2 命中即自动连边；L3/L4 命中需标注 `probable` 并在报告中列出；都不命中则保留为 `speculative` 或列为「疑似缺失接口」。

### 9.5 系统边界守卫策略（Scope Guard）

**要解决的问题**：Agent 在大目录里梳理时，很容易"顺手"读到隔壁项目，导致图谱里混进其他系统的节点，造成污染。边界必须在读取之前就确定，而不是读完之后再过滤。

**三层防御**

| 层级 | 机制 | 作用点 |
| --- | --- | --- |
| **L1 路径层（硬边界）** | 所有文件读取经过统一入口，路径必须命中 `scope.include` 前缀且不命中 `exclude`，否则直接拒绝 | 文件系统访问 |
| **L2 依赖层（软边界）** | 解析到系统外的包 / 服务 / 数据库引用时，不追进去，创建 `external` 边界节点并停止 | 依赖解析、链路追踪 |
| **L3 产物层（一致性校验）** | 组装图谱时校验所有节点的 `source.file` 是否都在白名单内，发现越界节点即报错并剔除 | 图谱组装 |

**边界节点处理规则**

| 情况 | 处理 |
| --- | --- |
| 调用第三方 HTTP API（如支付网关） | 建 `external` 节点，边类型用 `leaves-system`，标记"离开系统" |
| 依赖 npm / Maven 公共包 | **不建节点**（视为平台能力，噪声太大，可在配置中白名单化） |
| 依赖同组织的另一个系统 | 建 `external` 节点，并在报告中提示"存在跨系统依赖，考虑是否需要扩边" |
| 通过共享数据库表耦合 | 建 `external` 节点（`kind: shared-db`），标注为隐式耦合风险 |

**决策准则**：

1. **先定边界，再读代码** —— 边界未确认，不进入阶段 1。
2. **越界不静默** —— 阻断必须留痕，审计日志里每条都要有目标路径与触发阶段。
3. **边界外只记录不展开** —— 图谱要能说明"这里出去了"，但不假装理解外部系统。
4. **扩边要显式** —— 边界变更是一次有仪式感的操作，必须留痕并触发影响分析。
5. **公共依赖不算边界** —— 第三方库是平台能力，不是系统接口，避免图谱被噪声淹没。

### 9.6 增量更新推导规则（Git-Driven Incremental）

**要解决的问题**：每次全量重跑既贵又慢，且会让人重复确认已确认过的内容。多数提交实际只影响少数模块。

**推导链条**

```
Git diff（基线 → HEAD）
   ↓  文件级变更
[变更文件清单]  A / M / D / R / C
   ↓  按 source.file 反查
[直接受影响节点]
   ↓  沿图谱边扩散（按边类型分规则）
[影响半径]  必须重跑 / 契约重校验 / 数据重校验
   ↓  项目 + 模块聚合去重
[最小重跑集]  →  只梳理这些模块  →  合并回图谱
```

**边类型 → 影响扩散规则**

| 边类型 | 触发的影响 | 扩散范围 |
| --- | --- | --- |
| `imports` / `calls` | 直接代码依赖变更 | 同项目内，重跑源节点所在模块 |
| `exposes` | 接口定义变更 | 该接口的所有上游调用者需重校验 |
| `http-call` | 前端调用契约 | 触发跨项目契约重校验（前端 ↔ 后端） |
| `maps-to` | 实体与表映射变更 | 重跑 D3 数据访问子图 |
| `reads` / `writes` | 数据访问变更 | 重算该表的影响面（D3） |
| `fk` | 表关系变更 | 重算 D5 ER 子图 |
| `renders` / `uses-store` | 前端组件结构变更 | 重跑该页面链路（D4） |
| `leaves-system` | 边界调用变更 | 更新边界节点与"离系统点"标注 |

**必须升级为全量重跑的信号**

| 信号 | 原因 |
| --- | --- |
| 依赖清单发生实质性变更（框架 / ORM / 版本跃迁） | 技术栈判定可能失效，模板包要换 |
| 新增或删除项目 | 系统结构变化，跨项目边需重建 |
| 顶层目录结构重构 | 模块边界与 projectId 可能失效 |
| 路由注册方式变更（如整体换框架） | 接口识别规则失效 |
| 增量结果与全量结果不一致（抽样校验失败） | 推导规则本身有缺陷，需人工介入 |

**决策准则**：

1. **基线是锚**，没有基线就没有增量 —— 首次梳理必须是全量。
2. **只有 Git 不可用时才退回哈希**，且要明示精度下降。
3. **契约变更必须跨界重校验**，哪怕前端一行没改。
4. **拿不准就升级**：结构性变更一律走全量，宁可慢一次，不要错一版。
5. **增量必须语义等价于全量**，这是硬性验收指标（AC-18）。

## 10. 非功能需求

| 类别 | 需求 |
| --- | --- |
| **性能** | 单模块链路梳理 ≤ 5 min；10 万行代码规模的项目解构 ≤ 10 min；图谱首屏渲染（2000 节点）≤ 3 s |
| **可扩展性** | 新增技术栈仅需新增模板包，零核心代码改动；单系统支持 ≥ 20 个项目 |
| **范围隔离** | 范围守卫对越界读取的阻断率 100%，且阻断操作不产生任何副作用；审计日志完整可回溯 |
| **增量效率** | 典型小改动（1–5 个文件）的增量耗时 ≤ 全量的 20%；增量结果与全量结果语义等价 |
| **可靠性** | 任一阶段失败不得污染已有产物；所有写入采用「临时文件 + 原子替换」 |
| **可观测性** | 记录每阶段耗时、token 消耗、LLM 调用次数、识别命中率，输出 `.codeatlas/metrics.json` |
| **可移植性** | 支持 macOS / Linux；产物路径使用相对路径，保证仓库可迁移 |
| **安全性** | 代码默认不出本地；若使用云端 LLM，需提供"仅上传必要片段"与"完全离线（本地模型）"两种模式；上传前屏蔽密钥类文件（`.env`、`*.pem`、`credentials.*`） |
| **隐私** | 产物中不得包含源码全文，只保留结构性信息与必要片段 |
| **可用性** | 中断可续、失败可重试、错误信息需包含"发生了什么 + 可能原因 + 建议动作" |
| **兼容性** | 产物 Schema 版本化；大版本升级时提供迁移脚本 |
| **国际化** | v1 中文界面；文档语言可切换（中/英） |

## 11. 验收标准

### 11.1 功能验收

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-1 | 项目识别 | 在含 6 个项目的样例工作空间中，正确识别全部项目，无漏识、无误纳 |
| AC-2 | 技术栈判定 | Vue3 / React / Spring Boot / FastAPI / NestJS 各 1 个，判定语言与框架全部正确 |
| AC-3 | 解构完整性 | 样例系统的 30 个 API 中识别 ≥ 26 个（≥ 85% 召回） |
| AC-4 | 单模块链路 | 任选 1 个模块，梳理出的链路覆盖 DB → 后端 → 前端全路径，且每条边有源码证据 |
| AC-5 | JSON 契约 | 6 类产物全部通过 Schema 校验，无一条不符合 |
| AC-6 | 文档一致性 | Markdown 确认文档中的节点/关系与 JSON 完全一致（自动比对通过） |
| AC-7 | 断点续跑 | 人为中断后重启，能从中断模块继续，已完成模块不重跑 |
| AC-8 | 六维度展示 | D1–D6 均可正常渲染、切换、过滤 |
| AC-9 | 节点溯源 | 随机抽 20 个节点，100% 能定位到正确的源码位置 |
| AC-10 | 影响面分析 | 选定 1 张表，能列出全部读写它的代码路径 |
| AC-11 | **边界阻断** | 在工作空间内故意放置 1 个"系统外"项目，验证其代码零污染图谱，且审计日志有完整阻断记录 |
| AC-12 | **边界节点** | 系统中引用外部支付 API，图谱中出现 `external` 边界节点，且未被展开 |

### 13.2 开放问题（需在评审中拍板）

> ✅ 已确认：**交付形态 = CLI + Web**（`codeatlas <command>` + `codeatlas serve` 拉起本地画布）。

1. **LLM 依赖策略**：默认走云端还是本地模型？是否有"代码不出内网"的硬约束？
2. **渲染引擎**：Cytoscape.js vs React Flow，需结合前端团队技术栈定。
3. **首期技术栈范围**：建议按团队实际使用的技术栈排序，不做全量覆盖。
4. **产物存放位置**：`.codeatlas/` 放在工作空间内（便于版本管理、便于 gitignore 控制）还是集中存储（便于跨系统分析）？
5. **多项目是否同仓**：若各项目独立仓，`.codeatlas/` 需要一个独立载体目录；需明确该目录的归属与版本管理方式。
6. **是否需要与现有研发工具打通**：TAPD / CNB / GitHub / 工蜂 的项目、需求、代码库信息是否要纳入图谱？
7. **增量触发方式**：手动 `codeatlas update`、Git hook 自动触发、还是定时任务？建议 v1 手动 + 可选 hook。
8. **跨系统依赖的粒度**：当系统 A 依赖系统 B 时，只建 `external` 边界节点，还是需要"多系统联邦图谱"（v2 议题）？
9. **权限模型**：Web 端是否需要按角色区分可见维度？
10. **公共依赖白名单**：哪些第三方包算"平台能力"不建节点？需要一份默认规则 + 可配置。

## 附录 B. 决策准则速查表

> 供实现阶段快速取用。

### B1 识别策略

1. 能 AST 解析的，不用正则；能用正则的，不用 LLM。
2. 依赖清单 > 配置文件 > 目录结构 > 文件扩展名（判定证据优先级）。
3. 有 DDL 时以 DDL 为准，ORM 实体作为补充。
4. 模板包能覆盖的，不走通用降级模板。

### B2 置信度判定

| 场景 | 置信度 |
| --- | --- |
| 直接读到 import / 注解 / 路由字符串 | `certain` |
| 通过命名约定 + 结构推断 | `probable` |
| 通过 LLM 语义推断、无静态证据 | `speculative` |
| 用户已人工确认 | `certain` + `humanVerified` |

### B3 上下文管理

1. 任何未落盘的知识都视为已丢失。
2. 一次只处理一个模块，处理完立即落盘。
3. 注入上下文 = 已确认 JSON 摘要 + 当前模块必要源码片段。
4. 上下文用量达 80% 阈值时主动收尾落盘。

### B4 图谱渲染

| 场景 | 引擎 |
| --- | --- |
| 文档内 ≤ 20 节点 | Mermaid |
| 交互主画布 | Cytoscape.js |
| 印刷 / 导出 | Graphviz → SVG |
| > 2000 节点 | 聚合折叠模式 |

### B5 不确定性的处理

1. 宁可留「待确认」，不要编造连接。
2. 断链必须显式标注，不允许静默丢弃。
3. 所有 `speculative` 的边必须出现在报告的待确认清单中。

### B6 系统边界

1. 先定边界，再读代码；边界未确认不进入阶段 1。
2. 白名单外的路径一律阻断并留痕，不做"例外通融"。
3. 系统外部依赖只建 `external` 节点，记录关系，不展开内部。
4. 第三方公共包不建节点（平台能力，非系统接口）。
5. 扩边必须显式、留痕、触发影响分析。
6. 产物层必须回查一致性：任何 `source.file` 落在白名单外的节点都是缺陷。

### B7 版本增量

1. 首次必全量；没有基线就没有增量。
2. 变更以 Git diff 为准；Git 不可用才退回文件哈希，且需明示精度下降。
3. 影响扩散宁宽勿窄 —— 漏报比多跑更贵。
4. API 签名变更、DDL 变更必须跨项目重校验，即使调用方代码未动。
5. 结构性变更（新增/删除项目、依赖大改、目录重构）一律升级为全量重跑。
6. 增量结果必须语义等价于全量结果，否则视为缺陷。
7. 未受影响模块的人工确认状态必须保留，不要求用户重复确认。
