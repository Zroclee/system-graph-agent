| **增量失效算法** | 含跨项目契约扩散；缓存键必须含"依赖契约面哈希" | §9 |
| **增量默认保守升级** | 拿不准即全量，宁可慢一次不可错一版 | §9.4 |

## 1. 设计目标与不变量

### 1.1 设计目标

| # | 目标 | 度量方式 |
| --- | --- | --- |
| G1 | 同一份代码产出同一张图 | 同一 commit 连续两次全量运行，`graph.json` 字节级一致（除时间戳） |
| G2 | 增量结果与全量语义等价 | 增量跑完后与全量跑完的 `graph.json` 节点/边集合完全一致 |
| G3 | 每条边可溯源 | 100% 的边携带证据（文件 + 行号 + 片段），且片段可回验通过 |
| G4 | 上下文不丢失 | 任意时刻 kill 进程，重启后可从已完成模块继续，无重复劳动 |
| G5 | 智能可归因 | 每个 LLM 任务可独立开关，开关前后的召回率/误报率可对比 |
| G6 | 技术栈可扩展 | 新增一个技术栈只增加声明式模板，不改核心包代码 |

### 1.2 不变量（必须始终成立，违反即为缺陷）

| # | 不变量 | 违反后果 | 保障机制 |
| --- | --- | --- | --- |
| I1 | 所有文件访问经过 `ScopedFs` | 图谱被系统外代码污染 | §10 单一出口 + 架构测试 |
| I2 | 每个节点/边的 `source.file` 必落在白名单内 | 同上 | §5 S5 装配时校验，越界即剔除并记缺陷 |
| I3 | LLM 不直接写任何产物 | 幻觉进入事实源 | §7 propose → validate → commit |
| I4 | 每条边有证据且证据可回验 | 图谱不可信、无法定位问题 | §7 闸门二 |
| I5 | 节点 ID 由内容推导，不含行号/自增 | 增量 diff 全面失效 | §4.4 |
| I6 | SQLite 可从 JSON 事实源完全重建 | 索引损坏后数据不可恢复 | §8.3 重建一致性测试 |
| I7 | 模块缓存键包含其依赖契约面的哈希 | 后端改了 API 签名但前端模块命中缓存，漏重校验 | §9.3 |
| I8 | 增量推导拿不准即升级为全量 | 静默漏报，图谱悄悄过期 | §9.4 |

### 1.3 明确不做的事

- ❌ 不做运行时链路追踪（不接 APM / 埋点），只做**静态代码解构**
- ❌ 不做跨系统的全局图谱（边界由 `system.json` 硬性圈定，跨系统只建 `external` 节点）
- ❌ 不做代码修改或重构建议
- ❌ 不让 LLM 自由决定"下一步读哪个文件"（流水线顺序固定）

## 2. 总体架构

### 2.1 核心主张

> **代码能"证明"的，绝不给 LLM；代码只能"猜"的，交给 LLM 但限定在候选集内；两者都不行的交给人。**

这是全套设计的第一性原理，后续所有结构都是它的推论。

**为什么不做自主 Agent（ReAct / 工具循环）**：

| 维度 | 自主 Agent | 确定性流水线（本设计） |
| --- | --- | --- |
| 可复现 | 同一输入可能产出不同结果 | 除 LLM 任务外逐字节可复现 |
| 可增量 | 无法界定"重跑什么" | 阶段边界即失效最小单位 |
| 可验证 | 只能看最终结果对不对 | 每阶段产物可单独断言 |
| 成本 | 不可预估 | 设计期即可算出调用上限 |
| 调试 | 出错难归因 | 缺陷可定位到阶段、文件、行号 |

**Agent 性被保留在哪**：只有 S3 链路梳理内部，存在"下一个读哪个文件"的开放性，但也仅限在模块范围内的受控探索。其余全部是固定顺序。

### 2.2 分层

```
┌─ 入口层 ───────────────────────────────────────────┐
│  @codeatlas/cli            @codeatlas/web          │
└────────────────────┬───────────────────────────────┘
                     │
┌─ 编排层 ───────────▼───────────────────────────────┐
│  @codeatlas/pipeline                               │
│  StageRunner · 阶段调度 · 断点续跑 · --dry-run      │
│  · 审计留痕 · 缺陷收集                              │
└────────────────────┬───────────────────────────────┘
                     │
┌─ 阶段层（顺序固定）─▼───────────────────────────────┐
│  S0 圈定边界 → S1 技术判定 → S2 项目解构            │
│  → S3 链路梳理 → S4 人工确认 → S5 图谱装配          │
│  → S6 维度投影 → S7 渲染输出                        │
└────────────────────┬───────────────────────────────┘
                     │
┌─ 能力层（可插拔，唯一容纳智能）─────────────────────┐
│  @codeatlas/tech    技术栈模板（声明式）+ 判定器    │
│  @codeatlas/extract 提取器链：AST → 正则 → SQL      │
│  @codeatlas/llm     6 个 LlmTask + Provider 适配    │
│  （图谱投影器注册表：六个 Projector）                │
└────────────────────┬───────────────────────────────┘
                     │
┌─ 领域与基础层 ─────▼───────────────────────────────┐
│  @codeatlas/core   领域模型 · zod Schema · 图算法    │
│  @codeatlas/scope  ScopedFs 范围守卫（单一出口）     │
│  @codeatlas/store  JSON 事实源 · SQLite 索引 · 快照  │
│  @codeatlas/git    Git 适配 · changeset 推导         │
└────────────────────────────────────────────────────┘
```

### 2.3 数据流

```
源文件
  │  ①  ScopedFs 读取（唯一入口，白名单校验 + 审计）
  ▼
文件内容 + AST
  │  ②  提取器（纯函数：接收内容，不读文件）
  ▼
候选事实（API / 数据访问 / 组件 / 导入关系）
  │  ③  四道闸门（schema · 证据回验 · 置信度 · 冲突消解）
  ▼
事实源 JSON（.codeatlas/facts/**.json）
  │  ④  索引
  ▼
SQLite（可随时删除重建）
  │  ⑤  装配 + 冲突消解
  ▼
graph.json（节点 + 边）
  │  ⑥  六个 Projector 投影
  ▼
dimensions/d1..d6.json
  │  ⑦  渲染
  ▼
CLI 文本 / Mermaid / DOT  ·  Web 画布
```

关键：**LLM 只出现在 ② 的未命中分支**，且其产物同样要过 ③ 才能成为事实。LLM 不参与 ④⑤⑥⑦。

## 3. Monorepo 工程结构

### 3.1 包划分

采用 pnpm workspace + TypeScript project references。

```
codeatlas/
├── package.json                 # workspace root
├── pnpm-workspace.yaml
├── tsconfig.base.json
├── .dependency-cruiser.cjs      # 架构边界规则
├── packages/
│   ├── core/        @codeatlas/core
│   ├── scope/       @codeatlas/scope
│   ├── store/       @codeatlas/store
│   ├── git/         @codeatlas/git
│   ├── tech/        @codeatlas/tech
│   ├── extract/     @codeatlas/extract
│   ├── llm/         @codeatlas/llm
│   ├── pipeline/    @codeatlas/pipeline
│   ├── cli/         @codeatlas/cli
│   └── web/         @codeatlas/web
└── docs/                        # 本文档所在
```

| 包 | 职责 | 关键导出 |
| --- | --- | --- |
| `core` | 领域模型、zod Schema、图算法、ID 生成、纯工具函数 | `Node` `Edge` `Evidence` `Confidence` `Module` `TechTemplate`（**类型**） |
| `scope` | 白名单解析、`ScopedFs`、越界审计 | `ScopedFs` `Whitelist` |
| `store` | JSON 事实源读写、SQLite schema 与查询、内容寻址、快照、断点续跑 | `FactStore` `IndexStore` `SnapshotStore` |
| `git` | git 适配、changeset 推导 | `GitAdapter` `deriveChangeset()` |
| `tech` | 技术栈模板（**数据**）、判定器、模板注册表 | `templates/*` `detectStack()` `TemplateRegistry` |
| `extract` | 提取器实现、提取器注册表 | `Extractor` `extractors/*` |
| `llm` | `LlmTask` 接口、6 个任务实现、Provider 适配、调用留痕 | `LlmTask` `registry` `OpenAiCompatProvider` |
| `pipeline` | Stage 接口、Runner、S0–S7 实现、6 个 Projector | `Stage` `StageRunner` `stages/*` `projectors/*` |
| `cli` | 命令行入口 | `bin/codeatlas` |
| `web` | Web 服务与可视化画布 | — |

### 3.2 依赖规则矩阵

行 = 允许依赖的包，列 = 被依赖的包。

| ↓依赖者 \ 被依赖→ | core | scope | store | git | tech | extract | llm | pipeline |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **core** | — | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **scope** | ✓ | — | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **store** | ✓ | ✗ | — | ✗ | ✗ | ✗ | ✗ | ✗ |
| **git** | ✓ | ✗ | ✗ | — | ✗ | ✗ | ✗ | ✗ |
| **tech** | ✓ | ✗ | ✗ | ✗ | — | ✗ | ✗ | ✗ |
| **extract** | ✓ | ✗ | ✗ | ✗ | ✗ | — | ✗ | ✗ |
| **llm** | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | — | ✗ |
| **pipeline** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — |
| **cli** | ✓ | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ | ✓ |
| **web** | ✓ | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ | ✓ |

三条硬规则：

1. **`core` 是唯一的最内层**，不允许依赖任何 `@codeatlas/*`（只允许 `zod`）。
2. **中间层（scope / store / git / tech / extract / llm）互不依赖**。这是依赖倒置的落点：提取器需要技术栈模板，但 `extract` 不 import `tech`——模板的**类型**定义在 `core`，模板的**实例**由 `pipeline` 注入给提取器。
3. **`pipeline` 是唯一汇聚点**，`cli` / `web` 只能经由它访问中间层。

### 3.3 边界强制手段

规则不靠自觉，靠 CI 卡：

```js
// .dependency-cruiser.cjs 核心规则摘录
{
  name: 'core-must-be-leaf',
  severity: 'error',
  from: { path: '^packages/core/src' },
  to:   { path: '^packages/(?!core)' }
},
{
  name: 'no-cross-middleware',
  severity: 'error',
  from: { path: '^packages/(scope|store|git|tech|extract|llm)/src' },
  to:   { path: '^packages/(?!core)' }
},
{
  name: 'no-raw-fs-outside-io-packages',
  severity: 'error',
  from: { path: '^packages/(core|tech|extract|llm|pipeline)/src' },
  to:   { dependencyTypes: ['core'], path: '^(node:)?fs$' }
},
{
  name: 'only-io-packages-may-write',
  severity: 'error',
  from: { path: '^packages/(core|tech|extract|llm|git)/src' },
  to:   { path: '^(node:)?fs/promises$' }
}
```

`no-raw-fs-outside-io-packages` 是不变量 I1 的编译期保障：**阶段代码物理上无法直接读文件**，只能通过注入的 `ScopedFs`。

## 4. 领域模型与 Schema 策略

### 4.1 zod 为单一真源

**决策**：废弃手写 JSON Schema，改为 **zod 定义 → 自动导出 JSON Schema**。

```
packages/core/src/schema/
  ├── evidence.ts      → 导出 evidence.schema.json
  ├── module.ts        → 导出 module-index.schema.json
  ├── tech-profile.ts  → 导出 tech-profile.schema.json
  ├── graph.ts         → 导出 graph.schema.json
  ├── link.ts          → 导出 link.schema.json
  ├── system.ts        → 导出 system.schema.json
  └── changeset.ts     → 导出 changeset.schema.json
```

| 原因 | 说明 |
| --- | --- |
| 消灭类型漂移 | 手写 schema 与 TS 类型是两份真源，必然分叉 |
| 运行时与编译期同源 | 同一份 zod 既产出 TS 类型，又用于闸门一的运行时校验 |
| 文档自动同步 | `pnpm run schema:export` 重新导出，评审文档永远与代码一致 |

导出脚本产出到 `docs/02-设计/schemas/`，即上游文档引用位置保持不变。

> **迁移动作**：现有 6 份手写 schema 转为"由 zod 导出的生成物"，并在此目录加 `README` 标注"本目录文件自动生成，请勿手工编辑"。

### 4.2 核心实体

```ts
// ---- 证据 ----
interface Evidence {
  file: string;          // 相对系统根路径，必须落在白名单内
  line: number;          // 起始行号（1-based）
  snippet: string;       // 代码片段（原始文本，允许 LLM 被验证的锚点）
  extractorId: string;   // 产出该证据的提取器标识，如 'java.spring.route'
}

// ---- 置信度 ----
type Confidence = 'certain' | 'probable' | 'speculative';

// ---- 节点 ----
interface GraphNode {
  id: string;                    // 见 §4.4
  dimension: DimensionId;
  nodeType: NodeType;
  name: string;
  attrs: Record<string, unknown>;
  source: Evidence;              // 不变量 I2：装配时校验 file ∈ 白名单
}

// ---- 边 ----
interface GraphEdge {
  id: string;
  dimension: DimensionId;
  src: string;                   // NodeId
  dst: string;                   // NodeId
  edgeType: EdgeType;
  confidence: Confidence;
  evidence: Evidence[];          // 至少 1 条，闸门二强制
  producedBy: string;            // extractorId 或 llmTaskId —— 归因的关键字段
}

// ---- 事实（提取器输出，尚未过闸门）----
interface Candidate<T> {
  value: T;
  confidence: Confidence;
  evidence: Evidence[];
  producedBy: string;
}
```

`producedBy` 字段贯穿全程：它让"这条边是 LLM 猜的还是代码证的"成为可查询的数据，直接支撑 G5（智能可归因）。

### 4.3 六个图谱维度

维度不是六张独立的图，而是**同一份事实的六种投影**，定义写在 `core`：

```ts
interface DimensionDef {
  id: DimensionId;                  // 'd1'..'d6'
  name: string;
  nodeTypes: NodeType[];            // 节点类型白名单
  edgeTypes: EdgeType[];            // 边类型白名单
  layout: 'hierarchical' | 'force' | 'dagre';
  collapseBy?: NodeType;            // 默认折叠层级
}
```

| 维度 | 名称 | 节点类型 | 边类型 | 布局 |
| --- | --- | --- | --- | --- |
| D1 | 项目架构 | project, module | depends-on, contains | hierarchical |
| D2 | 前后端调用 | component, api | calls, renders | dagre |
| D3 | 数据访问 | module, table | reads, writes, fk | dagre |
| D4 | 端到端链路 | component, api, service, table | calls, invokes, reads, writes | dagre |
| D5 | 数据模型 | table, column | fk, pk-ref | force |
| D6 | 模块依赖 | module, external | depends-on, leaves-system | hierarchical |

---

### 4.4 节点 ID 规范

ID 格式：

```
NodeId := <nodeType> ":" <scope> ( ":" <discriminator> )*
```

| 节点类型 | ID 格式 | 示例 |
| --- | --- | --- |
| project | `project:<name>` | `project:backend` |
| module | `module:<project>:<moduleRelPath>` | `module:backend:src/main/java/com/acme/order` |
| service | `service:<project>:<fqSymbol>` | `service:backend:com.acme.order.OrderService` |
| api | `api:<project>:<METHOD>:<normalizedPath>` | `api:backend:GET:/api/v1/orders` |
| component | `component:<project>:<fileRelPath>` | `component:web:src/views/OrderList.vue` |
| route | `route:<project>:<path>` | `route:web:/order/list` |
| table | `table:<schema>:<tableName>` | `table:main:t_order` |
| column | `column:<schema>:<tableName>.<columnName>` | `column:main:t_order.id` |
| external | `external:<kind>:<identifier>` | `external:api:GET:/thirdparty/pay` |

**四条禁止**（直接对应不变量 I5）：

1. ❌ **禁止包含行号** —— 行号一动 ID 就变，全图 diff 爆炸，增量彻底失效
2. ❌ **禁止自增序号或随机 UUID** —— 无法与上一版对齐，无法判断"这是不是上次那个节点"
3. ❌ **禁止包含绝对路径** —— 换机器、换检出目录即失效；一律用相对系统根的路径
4. ❌ **禁止包含易变内容**（内容哈希、时间戳）—— 内容一改 ID 就变，增量会误判成"删节点 + 加节点"

#### 4.4.1 路径规范化算法（ID 生成与契约匹配共用）

```
/api/v1/orders/{orderId}   ─┐
/api/v1/orders/${orderId}   │
/api/v1/orders/:orderId     ├──►  /api/v1/orders/{p}
/api/v1/orders/[orderId]    │
/api/v1/orders/{id}/items   ─┘     /api/v1/orders/{p}/items
```

步骤：

1. 去掉末尾斜杠
2. 折叠重复斜杠
3. 按 `system.json` 声明的 `stripPrefixes` 剥离网关前缀（如 `/gateway`、`/api-gateway`）
4. 所有路径参数段统一替换为 `{p}`（覆盖 `{x}` `${x}` `:x` `[x]` 四种写法）
5. 查询串按白名单保留参与路由的参数，其余丢弃
6. 字面量数字段不归一化（`/orders/12345` 保持原样，它通常不是路由声明）

**为什么规范化必须进 ID**：如果 ID 用原始路径，`/orders/{id}` 和 `/orders/${id}` 会生成两个节点，前后端永远匹配不上。规范化之后，跨项目契约匹配从"模糊匹配问题"降级为"**ID 相等判断**"——这是把原本可能交给 LLM 的活儿抢回代码手里的关键一手。只有规范化后仍不等的（如 `/order` vs `/orders`）才落到 L1 语义对齐。

## 5. 阶段契约（S0–S7）

### 5.1 阶段总览

| 阶段 | 输入 | 输出 | 执行者 | 重跑粒度 | 幂等 | 含 LLM |
| --- | --- | --- | --- | --- | --- | --- |
| **S0** 圈定边界 | `system.json` | `whitelist.json` `audit` | 代码 | 整系统 | ✓ | — |
| **S1** 技术判定 | 各项目根 | `tech-profile.json` | 代码 | 单项目 | ✓ | L6 |
| **S2** 项目解构 | `tech-profile` | `module-index.json` | 代码 | 单项目 | ✓ | L4 |
| **S3** 链路梳理 | `module-index` `tech-profile` | `link/<moduleId>.json` `confirm/<moduleId>.md` | 代码 | **单模块** | ✓ | L1 L2 L3 |
| **S4** 人工确认 | `link/*.json` | 状态流转 `pending→confirmed` | 代码 + **人** | 单模块 | ✓ | L5 |
| **S5** 图谱装配 | confirmed links | `graph.json` | 代码 | 全量 | ✓ | — |
| **S6** 维度投影 | `graph.json` | `dimensions/d1..d6.json` | 代码 | 全量 | ✓ | — |
| **S7** 渲染输出 | `dimensions/*` | 文本 / Mermaid / DOT / 画布 | 代码 | 全量 | ✓ | — |

**流水线约定**：`Stage<In, Out>` 统一接口，接受 `PipelineContext`（含 `systemId`、`scopedFs`、`factStore`、`indexStore`、`logger`、`llmRegistry`、`dryRun`）。断点续跑、审计、缺陷收集、`--dry-run` 全部在 `StageRunner` 里实现一次，阶段实现者不感知。

```ts
interface Stage<In, Out> {
  readonly id: 'S0' | 'S1' | 'S2' | 'S3' | 'S4' | 'S5' | 'S6' | 'S7';
  readonly rerunGranularity: 'system' | 'project' | 'module' | 'full';
  /** 是否可跳过（依据指纹）；S5–S7 恒返回 false */
  canSkip(ctx: PipelineContext, input: In): Promise<boolean>;
  run(ctx: PipelineContext, input: In): Promise<Out>;
}
```

### 5.2 S0 圈定边界

| 项 | 内容 |
| --- | --- |
| 输入 | `system.json`（用户声明：系统名、项目白名单、根路径、`stripPrefixes`） |
| 输出 | 规范化白名单（含 `realpath` 解析结果）、初始审计记录 |
| 失败模式 | 白名单为空 → **立即中止**，不进入 S1；路径不存在 → 记为缺陷并剔除该项目 |
| 关键动作 | 对每个白名单根做 `realpath`，落库真实路径；建立 `ScopedFs` 单例 |

> **符号链接陷阱**：白名单校验必须在 `realpath` 之后进行。否则可以通过一个指向系统外的软链绕过守卫。本项目自身不再跟随额外软链层级。

### 5.3 S1 技术判定

| 项 | 内容 |
| --- | --- |
| 输入 | 各项目根目录 |
| 输出 | `tech-profile.json`：每项目的栈、框架、版本、入口约定、模板 id |
| 主要手段 | 读 manifest：`package.json` / `pom.xml` / `build.gradle` / `requirements.txt` / `pyproject.toml` / `go.mod` |
| 判定依据 | 依赖特征（如 `vue@3` + `vite` → `vue3-vite`）+ 配置特征（`vue.config.js` vs `vite.config.ts`）+ 文件特征（`.vue` 存在） |
| 失败模式 | manifest 缺失或信号矛盾 → 触发 **L6**；L6 也失败 → 标记 `unknown`，**不中止**，但 S2/S3 对该项目降级为"整项目单模块 + 仅正则提取" |

### 5.4 S2 项目解构

| 项 | 内容 |
| --- | --- |
| 输入 | `tech-profile.json` |
| 输出 | `module-index.json`：模块清单（id、相对路径、类型、构建单元归属） |
| 模块划分依据 | 优先级：① 构建单元（Maven module / workspace package）② 模板声明的模块约定（如 Spring 的 `@Service` 包根、Vue 的 `views/` 目录）③ 目录层级 + 文件数阈值 |
| 执行者 | 代码划分 + **L4** 生成业务摘要与标签（可降级为目录名） |
| 失败模式 | 模块划分失败 → 退化为"整个项目 = 一个模块"，仍可继续 |

> **「模块」是整个系统的原子单元**：它是 S3 的重跑粒度、S4 的确认粒度、断点续跑的检查点粒度。模块划分粒度直接决定增量效率——太粗则每次重跑过重，太细则确认负担过重。默认建议维持在**业务域级别**（如 `order`、`user`、`payment`），而非包级别。

### 5.5 S3 链路梳理（核心阶段）

S3 按模块逐个执行，模块内部分六个子步骤：

| 子步骤 | 动作 | 执行者 |
| --- | --- | --- |
| 3.1 API 提取 | 扫路由注解/装饰器/函数调用 → API 清单；类级前缀 + 方法级路径拼接；签名与参数 | 代码（+ **L2** 动态路由） |
| 3.2 数据访问提取 | ORM 实体 ↔ 表映射；Repository/Mapper 静态 SQL；裸 SQL 表名抽取 | 代码（+ **L3** 动态 SQL） |
| 3.3 前端调用提取 | HTTP 客户端调用点；组件 → store → api 模块 → HTTP 调用链；路由 ↔ 页面映射 | 代码 |
| 3.4 契约匹配 | 前端调用 URL ↔ 后端 API：**先 ID 相等，再规范化相等，最后才 L1 语义对齐** | 代码 → **L1** |
| 3.5 模块依赖 | 后端 import / 依赖注入图；跨模块 service 调用 | 代码 |
| 3.6 证据与置信度 | 记录 `文件:行号 + 片段`；按提取器来源打分；初步去重 | 代码 |

**输出**（每个模块两份）：

- `link/<moduleId>.json` —— 结构化事实，供 S5 消费
- `confirm/<moduleId>.md` —— 人类可读的确认文档，供 S4 评审（含 **L5** 生成的链路业务说明）

**为什么同时产出 JSON 和 Markdown**：JSON 给机器，Markdown 给人。人工确认的输入必须是可读的，否则确认动作会退化成"无脑点通过"。这也正是需求里"在文档确认 JSON 对应节点信息、业务逻辑"的落点。

### 5.6 S4 人工确认

| 项 | 内容 |
| --- | --- |
| 输入 | `confirm/<moduleId>.md` + `link/<moduleId>.json` |
| 输出 | 模块状态：`pending → confirmed` / `rejected` / `corrected` |
| 执行者 | **人**（这是唯一的强人工闸门） |
| 规则 | **S5 只消费 `confirmed` 与 `corrected` 的模块**；`pending` 模块以"低可信"标记进入图谱并在报告中标红，`rejected` 模块整体排除 |
| 失败模式 | 全部 `pending` → 图谱仍可产出，但报告显著标注"未经人工确认" |

### 5.7 S5 图谱装配

| 项 | 内容 |
| --- | --- |
| 输入 | 所有 confirmed / corrected 的 `link/*.json` |
| 输出 | `graph.json`（nodes + edges + dimensions 定义） |
| 动作 | ① 节点去重（按 ID）② 边合并（同 `src+dst+type` 合并且证据取并集）③ 冲突消解（§7 闸门四）④ **白名单校验**（不变量 I2，越界即剔除并记缺陷）⑤ 孤岛节点与悬挂边检测 |
| 失败模式 | 校验不过的节点被剔除，`graph.json` 仍产出，缺陷汇总进报告 |

> **悬挂边**是重要信号：某条边的 `src` 或 `dst` 节点不存在，通常意味着"前端调了一个后端没实现的接口"（或反之，漏识别）。这类边不静默删除，而是以 `dangling: true` 保留，单独成一张风险清单。

### 5.8 S6 维度投影

六个 `Projector` 从同一份 `graph.json` 投影。`Projector` 是纯函数，`(graph, dimDef) => DimensionGraph`。

| 投影动作 | 说明 |
| --- | --- |
| 过滤 | 按 `dimDef.nodeTypes` / `edgeTypes` 白名单裁剪 |
| 折叠 | 按 `dimDef.collapseBy` 把子节点折叠到父节点（如 D1 把 api 折进 module） |
| 聚合 | 折叠后合并重复边，权重累加 |
| 布局参数 | 带上 `layout` 供渲染层使用 |

### 5.9 S7 渲染输出

| 通道 | 形态 |
| --- | --- |
| CLI | 文本树、Mermaid、DOT、CSV；`--dimension d4` 切换维度 |
| Web | 服务端读 `dimensions/*.json`，前端画布渲染（G6 / Cytoscape），支持维度切换、层级折叠、节点溯源跳转 |

**CLI 先于 Web**：Mermaid / DOT 能在 PR、文档、终端里直接看，是验证图谱正确性的最快通道。Web 画布解决的是"好看与好用"，不是"对不对"。

## 6. LLM 任务规格

### 6.1 通用接口

```ts
interface LlmTask<In, Out> {
  readonly id: string;          // 'L1' .. 'L6'
  readonly enabled: boolean;    // feature flag，默认 false
  /** 输入必须有界：由调用方裁剪好，禁止传整个仓库 */
  buildPrompt(input: In): { system: string; user: string };
  /** 输出必须可校验 */
  readonly schema: z.ZodType<Out>;
  /** 必须有确定性兜底；返回 null 表示放弃该项，标记未识别 */
  fallback(input: In): Out | null;
  readonly budget: { maxInputTokens: number; timeoutMs: number; retries: number };
  /** 同输入不重复调用 */
  cacheKey(input: In): string;
}
```

三条硬约束：

1. **`fallback` 是必填字段** —— 由 TypeScript 在编译期强制。写不出 fallback 的任务，说明它本该是确定性能力，不该出现在这个接口里。
2. **`enabled` 默认 `false`** —— v1 全部关闭，先跑纯确定性基线。
3. **所有调用写入 `llm_call` 表** —— 可归因、可对比、可回放（§8.2）。

### 6.2 任务清单

| ID | 任务 | 触发条件 | 输入边界 | 输出 schema | fallback | 调用量级 |
| --- | --- | --- | --- | --- | --- | --- |
| **L1** | 契约语义对齐 | 3.4 中 ID 相等与规范化相等均不成立，但存在候选集 | 前端调用点（URL、方法、所在文件片段）+ 后端候选 API 列表（**≤5 条**） | `{ apiId, reason, confidence }` | 返回 `null` → 记入人工清单 | 按未命中调用点数 |
| **L2** | 动态路由解释 | 路由非静态声明（配置 / DB 驱动） | 注册点代码片段 + 相关配置片段 | `{ routes: [{ method, path, evidence[] }] }` | 记为「动态路由·未展开」 | 按动态注册点数（罕见） |
| **L3** | 动态 SQL 解释 | 表名来自字符串拼接或运行时变量 | SQL 构造代码片段 + 已抽出的字面表名线索 | `{ tables: string[] }` | 抽字面表名，动态部分标 `unknown` | 按动态 SQL 点数 |
| **L4** | 模块业务摘要 | S2 每模块一次 | 模块路径 + 文件名列表 + 主要符号名（**不传源码**） | `{ summary, tags[] }` | 目录名 + 主要符号名 | = 模块数 |
| **L5** | 链路业务说明 | S4 每模块一次 | **只传已确认的结构化链路事实，不传源码** | `{ markdown }` | 用事实拼模板文案 | = 模块数 |
| **L6** | 技术栈兜底判定 | manifest 缺失或信号矛盾 | 目录树摘要 + 配置文件清单 | `{ stack, version, evidence }` | 返回 `null` → 标 `unknown` 交人工 | 按异常项目数（罕见） |

> **注意 L4 / L5 的输入设计**：两者都**不传源码**。原因是业务含义往往已经浓缩在"API 路径 + 表名 + 符号名"里了（`/api/v1/orders` + `t_order` → 订单模块）。**由代码先把语义浓缩好，再让 LLM 做命名和表达**，既省 token 又比"让模型读代码猜业务"更准。这条直接决定了 LLM 的成本量级。

### 6.3 开关与归因

| 机制 | 说明 |
| --- | --- |
| 逐项开关 | `codeatlas.config.json` 中 `llm.tasks: { L1: false, L4: true, ... }` |
| 调用留痕 | 每次调用写 `llm_call`（`taskId` `cacheKey` `inputHash` `output` `model` `tokensIn` `tokensOut` `latencyMs` `ok` `fallbackUsed`） |
| 效果对比 | 报告输出「任务开关矩阵 × 召回率 / 误报率」对比表，回答"开这一个值不值" |
| 优雅降级 | 关闭任意任务后，其 fallback 路径自动生效，**图谱仍完整产出**，只是该部分质量下降 |

### 6.4 反蔓延准则

| # | 准则 | 违反信号 |
| --- | --- | --- |
| 1 | 写不出 fallback 的任务，不该交给 LLM | 接口层报错（编译期） |
| 2 | LLM 任务总数应是个位数 | 本设计 6 个；若涨到 15 个，说明把该代码做的事推给了模型 |
| 3 | LLM 永不直接写产物 | 出现 `graph.json` 中被 LLM 直接写的字段 |
| 4 | 调用次数在设计阶段可算出上限 | 算不出来 → 说明边界没画清，先回去画边界 |

## 7. 四道闸门与证据回验

### 7.1 闸门总览

**所有候选事实**（无论来自提取器还是 LLM）在写入事实源之前，必须依次通过四道闸门：

| # | 闸门 | 校验内容 | 不通过的处理 |
| --- | --- | --- | --- |
| **一** | Schema 校验 | 按 zod schema 解析 | 整体丢弃，记 `defect`，走 fallback |
| **二** | 证据回验 | 打开源文件，验证 `line` 处的 `snippet` **真实存在** | **丢弃该项**（反幻觉的核心闸门） |
| **三** | 置信度不得自升级 | LLM 产物上限 `speculative`；多来源取最低值 | 强制降级到允许值 |
| **四** | 冲突消解 | 同 `src + dst + type` 的边合并：`certain > probable > speculative`；同级取证据并集 | 保留高置信度边，低者降为备选证据 |

### 7.2 证据回验的实现

```
evidenceSnippetMatches(evidence, scopedFs) -> boolean
  1. content  = scopedFs.read(evidence.file)        // 白名单校验在内
  2. lines    = content.split('\n')
  3. window   = lines[line-1-delta .. line-1+delta+snippetLines]   // delta 默认 2
  4. return normalize(window) === normalize(evidence.snippet)
        // normalize：去首尾空白、折叠内部连续空白、统一换行符
```

**为什么这是"硬"机制**——伪造一条证据需要同时满足三个条件：

1. 文件路径在白名单内 **且** 文件真实存在
2. 行号定位到的窗口内容与声称的片段一致
3. 片段本身与源文本逐字符（归一化后）相同

三者同时为真，才可能伪造成功。门槛高到 LLM 基本不可能蒙混过关。

### 7.3 为什么闸门必须前置

图谱一旦落盘，后续所有阶段（装配、投影、渲染、增量复用）都会**无条件信任**它。事后再校验等于让污染先流到终点再回头找。**闸门必须卡在"写入事实源之前"这一刻，而不是"生成报告之后"。**

### 7.4 缺陷（Defect）分类

| 类别 | 含义 | 严重度 |
| --- | --- | --- |
| `schema-invalid` | LLM 或提取器输出不符合 schema | 低（已丢弃） |
| `evidence-mismatch` | 证据回验失败 | **高**（意味着幻觉或解析错误） |
| `out-of-scope` | `source.file` 落在白名单外 | **高**（边界守卫被突破） |
| `dangling-edge` | 边的端点节点不存在 | 中（可能是死代码或漏识别） |
| `unresolved` | 三级降级均未命中 | 中（计入覆盖率缺口） |
| `low-trust-module` | 模块缺陷率超过 50% | 高（该模块产出不可信） |

`evidence-mismatch` 与 `out-of-scope` 两类为**高严重度**，任一出现都应在报告中显著提示，不应被淹没在统计数字里。

## 8. 存储设计

### 8.1 双存储职责划分

> **JSON 是事实源，SQLite 是派生索引。SQLite 可以随时删掉重建，且重建结果必须与增量维护的结果一致（不变量 I6）。**

| | JSON 事实源 | SQLite 派生索引 |
| --- | --- | --- |
| 位置 | `.codeatlas/facts/` `graph/` | `.codeatlas/index.db` |
| 角色 | **唯一的真相** | 查询与推理的加速层 |
| 可 diff | ✓ 可 code review | ✗ 二进制 |
| 可入 Git | ✓ | ✗（加入 `.gitignore`） |
| 人工确认载体 | ✓（Markdown + JSON） | ✗ |
| 崩溃恢复 | 原子 rename 即可 | 可从 JSON 重建 |
| 大系统查询 | 全量加载不可行 | ✓ 索引 + 图遍历 |

**为什么不让 SQLite 当真源**：人工确认需要**可读、可 diff、可评审**的文本；图谱的每一次变化都应该能进 PR 被人看到。二进制库做不到这一点。而 SQLite 的价值在**查询**——增量失效需要回答"哪些模块引用了这个 API"，这个用 SQL 现成索引是毫秒级，用 JSON 全量遍历是分钟级。

### 8.2 SQLite 表结构

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL              -- schema_version / fact_source_hash / last_full_run_at
);

CREATE TABLE system (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL,
  root_path  TEXT NOT NULL,
  created_at TEXT NOT NULL
);

CREATE TABLE project (
  id            TEXT PRIMARY KEY,
  system_id     TEXT NOT NULL REFERENCES system(id) ON DELETE CASCADE,
  name          TEXT NOT NULL,
  rel_path      TEXT NOT NULL,
```

## 9. 增量失效算法

### 9.1 变更集推导

```
1. git diff --name-status <from>..<to>          → D（变更文件集，含 A/M/D/R）
2. ∀ d ∈ D：查 file 表 → 所属 module m → A₀ = ∪ { m }
3. 结构敏感文件检测（命中任一 → 置全局失效信号）：
   - 依赖清单：package.json / pom.xml / build.gradle / requirements.txt / go.mod
   - 工作区与构建配置：pnpm-workspace.yaml / tsconfig*.json / vite.config.* / settings.gradle
   - 项目新增或删除（顶层目录数量变化）
   - .codeatlas/system.json 自身变更
   - 提取器版本或技术栈模板版本升级
```

### 9.2 影响扩散（必须跨项目）

```
A ← A₀ ;  队列 ← A₀
while 队列非空:
    m ← 队列.pop()
    // ① 契约扩散：m 暴露的 API 的所有消费者
    for api ∈ apis(m):
        for consumer ∈ reverseIndex[api.id]:
            if consumer ∉ A: A.add(consumer); 队列.push(consumer)
    // ② 数据耦合扩散：m 访问的表的所有其他访问者
    for t ∈ tables(m):
        for other ∈ reverseIndex[t]:
            if other ∉ A: A.add(other); 队列.push(other)
    // ③ 共享库扩散
    for ref ∈ reverseIndex[module:m]:
        if ref ∉ A: A.add(ref); 队列.push(ref)
```

**① 是跨项目的**：后端改了一个 API，前端消费它的模块必须一起重校验。这是"图上的影响扩散"区别于"文件哈希比对"的核心所在。

### 9.3 模块指纹（缓存键）

```
fingerprint(module) = H(
      ⊕ H(该模块下所有文件的 sha256)
    + H(提取器版本 extractorVersion)
    + H(模板版本 templateVersion)
    + H(该项目 tech-profile 的哈希)
    + H(依赖契约面 dependentContractSurface)     ← 最容易漏的一条
)
```

`dependentContractSurface` 的定义：

| 模块角色 | 契约面内容 |
| --- | --- |
| 前端模块 | 它调用的所有后端 API 的**规范化签名集合**（method + normalizedPath + 参数结构摘要） |
| 后端模块 | 它访问的所有表的 **DDL 摘要**（列名 + 类型） |
| 被依赖模块 | 它对外暴露的符号签名摘要 |

> **为什么必须包含这一项**（不变量 I7）：假设后端把 `POST /orders` 的请求体从 `{ sku, qty }` 改成 `{ sku, quantity }`，前端代码一行未动。如果前端模块的指纹只看自己的源码哈希，它会**命中缓存直接跳过**，跨项目契约永远得不到重校验。这是最隐蔽的一类漏报——图看着是完整的，但内容已经过期。

### 9.4 保守升级规则

| 情况 | 判定 |
| --- | --- |
| 结构敏感文件变更 | **升级全量** |
| 无法定位变更文件所属模块 | **升级全量** |
| 非 Git 项目（哈希降级路径） | **升级全量**，并在报告标注"精度下降" |
| `--dry-run` 得到的重跑集 > 全量模块数的 60% | **升级全量** |
| 扩散链条深度 > 8 层 | **升级全量**（疑似误连边导致爆炸） |

一句话准则：**宁可慢一次，不要错一版。** 增量漏报的代价远高于多跑一次全量。

### 9.5 重跑集与等价性

| 阶段 | 增量时的处理 |
| --- | --- |
| S0 | 仅当 `system.json` 变更时重跑，否则复用 |
| S1 | 仅重跑变更文件所属项目 |
| S2 | 仅重跑受影响模块所属项目 |
| S3 | **仅重跑 A 中的模块**（核心收益点） |
| S4 | 状态保留；**被重跑过的模块状态回退为 `pending`** |
| S5 S6 S7 | **恒全量**（纯投影，便宜且必须一致） |

> S4 这条容易漏：模块代码变了，人确认过的结论就过期了。**变更必须使确认失效**，否则图谱会带着"已被确认"的假象继续传播错误。

**等价性验证（G2）**：`codeatlas verify --incremental-vs-full` —— 对同一 `to_sha` 分别用增量和全量产出 `graph.json`，节点集与边集必须完全一致，否则判为缺陷。

## 10. 范围守卫设计

### 10.1 单点收口

所有文件访问经 `ScopedFs`，它是 scope 包唯一导出的 IO 入口。

```ts
class ScopedFs {
  constructor(roots: ResolvedRoot[], auditor: Auditor) {}

  async read(rel: string): Promise<string>;      // 越界 → throw ScopeViolation
  async glob(patterns: string[]): Promise<string[]>;
  async stat(rel: string): Promise<Stat>;
  async realpath(rel: string): Promise<string>;
}
```

- 所有路径先 `resolve` 再 `realpath`，然后做 `startsWith(root)` 校验
- 越界**不静默**：写审计 + 抛 `ScopeViolation`
- 阶段代码**物理上拿不到** `fs`（由 §3.3 的架构测试强制）

### 10.2 四层防御

| 层 | 机制 | 拦什么 | 代码落点 |
| --- | --- | --- | --- |
| **L1** 路径层 | 白名单外读取直接拒绝 + 审计 | 提取器"顺手"读隔壁目录 | `ScopedFs` |
| **L2** 依赖层 | 系统外引用建 `external` 节点，不展开内部 | 顺着 import / API 调用爬出去 | S3.5 依赖解析器 |
| **L3** 产物层 | 装配时校验所有 `source.file` 在白名单内，越界即剔除 | 前两层漏网的 | S5 装配 |
| **L4** 链接层 | `realpath` 后再校验，防软链逃逸 | 用软链绕过路径检查 | `ScopedFs.realpath` |

**L3 是最后一道闸**——它保证图谱里每个节点都能自证"我属于这个系统"，这是防污染的根本保障，而不是靠流程自觉。

### 10.3 边界节点策略

| 类别 | 是否建节点 | 理由 |
| --- | --- | --- |
| 第三方公共包（npm / Maven / pip） | ❌ 不建 | 平台能力，全建进来图谱会被噪声淹没 |
| 外部系统（他方服务） | ✓ `external:service:*` | 需要知道系统依赖了谁 |
| 共享库（自研跨系统包） | ✓ `external:lib:*` | 其变更会同时影响多个系统 |
| **共享数据库表** | ✓ 标 `shared: true` | **最隐蔽的跨系统耦合**：不体现为任何 API 调用 |
| 本系统内的其他项目 | ✓ 正常节点 | 属于边界内 |

## 11. 错误处理与断点续跑

### 11.1 Result 而非抛异常

```ts
type Result<T> =
  | { ok: true;  value: T }
  | { ok: false; defect: Defect };
```

一个万文件级别的长跑，单个文件解析失败不该中断整轮。每个文件级操作返回 `Result`，失败收集进 `defect` 表，轮末汇总成报告。

**例外**：`ScopeViolation` 与 `SchemaInvalid`（系统级配置错误）**应当抛出并中止**——因为它们意味着前提假设已经被打破，继续跑只会产出垃圾。

### 11.2 原子写

```
写 facts/link/<moduleId>.json:
  1. write   → facts/.tmp/<uuid>.json
  2. fsync
  3. rename  → facts/link/<moduleId>.json      // 同文件系统内 rename 是原子的
```

保证任意时刻 kill 进程都不会留下半截 JSON。

### 11.3 断点续跑

| 机制 | 说明 |
| --- | --- |
| 检查点粒度 | **每个模块**（S3 完成后立即落盘 + 更新 `module.fingerprint`） |
| 恢复 | `codeatlas run --resume`，`fingerprint` 未变的模块直接跳过 |
| 进度可见 | `codeatlas status` 输出模块完成率、缺陷率、待确认数 |
| 幂等 | S0–S4 均幂等，重复执行不产生重复事实 |

| 里程碑 | 内容 | 验收标准 |
| --- | --- | --- |
| **M0 地基** | monorepo 骨架、`core` 领域模型 + zod schema、`ScopedFs`、`Store`（JSON + SQLite schema）、`StageRunner`、dependency-cruiser 规则 | 架构测试全绿；`core` 零 IO 依赖 |

| **M2 铺栈** | 技术栈模板扩展到 6–8 个常用栈，提取器补全 | 每个新增栈只增加模板数据，核心零改动 |
| **M3 增量** | git 适配、changeset、fingerprint、影响扩散、等价性验证 | `--incremental-vs-full` 一致率 100% |
| **M4 智能** | 6 个 LLM 任务（默认关闭）+ 开关矩阵 + 效果对比报告 | 每个任务可独立开关且能给出召回率增量 |

| **M6 闸门打磨** | confirm 文档体验、批量确认、修正回写 | 单模块确认耗时 < 3 分钟 |

> **M1 是整个项目最关键的一步**。它验证的不是"能不能跑通"，而是"**提取精度到底够不够用**"。如果竖切跑完发现一条链路的召回率只有 50%，那说明模板设计或提取策略需要返工——这个结论越早知道越好，横向铺开 8 个技术栈之后才发现就晚了。

## 附录 A：设计准则速查

1. **代码能证明的，绝不给 LLM** —— 三级判定：字面证明 → 规则推导 → 语义判断
2. **LLM 只提议，不落库** —— 所有候选过四道闸门才进事实源
3. **证据必须回验** —— 路径存在、行号命中、片段一致，三者同时为真
4. **ID 内容寻址** —— 禁行号、禁自增、禁 UUID、禁绝对路径
5. **缓存键含依赖契约面** —— 否则后端改签名、前端命中缓存，静默漏报
6. **拿不准就升级全量** —— 宁可慢一次，不要错一版
7. **范围守卫单点收口** —— 阶段代码物理上拿不到 `fs`
8. **写不出 fallback 的任务不该给 LLM** —— 编译期强制
9. **变更即确认失效** —— 模块重跑后状态回退 `pending`
10. **任何未落盘的知识都视为已丢失** —— 以模块为检查点，原子写盘
