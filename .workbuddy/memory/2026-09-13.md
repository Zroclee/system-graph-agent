## 架构设计讨论（纯 TS 实现）

**用户诉求**：讨论 CodeAtlas 用纯 TypeScript 实现时的设计模式。**已确认交付形态 CLI + Web。**

**我给出的核心主张**：不做「自主 Agent」，做「**确定性流水线 + 受控智能**」。三条依据：可复现（AC-18 增量与全量语义等价需可验证）、可增量（阶段边界 = 失效最小单位）、成本可控。

**分层架构（5 层）**：入口层（CLI / Web）→ 编排层（Pipeline Runner：阶段调度、断点续跑、dry-run、审计）→ 阶段层（S0 圈定边界 / S1 技术判定 / S2 项目解构 / **S3 链路梳理（唯一含 LLM）** / S4 人工确认 / S5 图谱装配 / S6 维度投影 / S7 渲染）→ 能力层（技术栈模板注册表 / 提取器链 / 图谱投影器注册表 / LLM 解释器）→ 领域与基础层（领域模型 zod / ScopedFs / 内容寻址产物存储 / Git·LLM Provider）。

**七条设计模式**：① 分阶段流水线（非自主 Agent）② 策略+注册表（模板/提取器/投影器）③ 责任链降级（AST→正则→LLM）④ 门面+守卫（ScopedFs 单点收口）⑤ 事件溯源+物化视图（module-link/*.json → graph.json）⑥ 内容寻址缓存（增量指纹）⑦ 两阶段提交+人工闸门（pending→confirmed）。

**LLM 边界（关键）**：窄接口纯函数，非会用工具的 Agent。三级降级产出候选边 → 四道闸门（zod Schema 校验 / 证据必填 / 置信度不得自升级 / 冲突消解 certain>probable>speculative）→ 才写 graph.json。**propose → validate → commit**。LLM 跨步骤不持有状态，状态全在 JSON——即「无状态 worker + 外部记忆」。

**三个易翻车细节**：① 节点 ID 必须可推导（内容寻址，如 `维度:路径#符号`），不能用自增/UUID，否则增量无法对齐；② 缓存键必须含提取器/模板版本，否则升级解析器后拿到陈旧结果；③ Schema 单一真源改为 zod → 自动导出 JSON Schema，替代手写 6 份 schema 避免漂移。

**待用户拍板**：Q1 v1 是否先不接 LLM（我倾向先跑通确定性管道并量化召回率，LLM 作为 v2 精度补丁）；Q2 单包多目录 vs monorepo（我倾向单包 + dependency-cruiser 守边界，稳定后再拆）；Q3 规模预期与是否上 SQLite。
