# 2026-09-10

## 新增项目：CodeAtlas 系统图谱梳理工具（需求文档阶段）

**背景**：用户要做一个工具，输入一个工作空间（内含前后端等多项目代码），由 agent 梳理出系统图谱 —— 覆盖 API、前后端调用、后端数据库访问、模块调用等关联关系，最后按多维度图表展示。

**本次产出**

- 新建 `docs/` 目录
  - `docs/需求文档-系统图谱梳理工具.md` —— 主需求文档 v0.1，按标准 PRD 结构 + EARS 原则撰写。含：背景痛点（P1–P6）、产品定位与目标用户、术语与层级模型、六阶段主流程、功能需求 F1–F8、数据模型、技术栈模板库、图谱维度定义、技术方案与决策准则、非功能需求、验收标准（AC-1～AC-16）、里程碑 M1–M5、风险 R1–R8、待确认问题 Q1–Q8、决策准则速查表。
  - `docs/schemas/` —— 5 份 JSON Schema，作为工具中间产物契约：`workspace` / `tech-profile` / `module-index` / `graph` / `link`。全部通过 JSON 语法校验。

**关键设计决策（已写入文档，待评审确认）**

1. **六阶段流程**：工作空间接入 → 技术栈判定 → 项目解构 → 链路梳理 → 图谱组装 → 维度化展示。产物统一落盘到 `<workspace>/.codeatlas/`。
2. **模板包（Template Pack）机制**：每种技术栈（vue3 / react / spring-boot / fastapi / nestjs …）一份声明式 `template.yaml`，定义去哪找 API、组件、模块、数据访问。新增技术栈零核心代码改动。
3. **防上下文丢失的核心机制**：以「模块」为原子单元，每模块梳理完立即落盘 JSON + Markdown 确认文档，`progress.json` 支持断点续跑。原则：**任何未落盘的知识都视为已丢失**。
4. **静态解析 vs LLM 的分工准则**：能 AST 解析的不用正则，能用正则的不用 LLM。每条边必须带证据（file:line）与置信度（certain / probable / speculative）。
5. **六种图谱维度**：D1 项目架构、D2 前后端调用、D3 数据访问、D4 端到端链路、D5 数据模型、D6 模块依赖。同一份 graph.json 按「节点类型白名单 + 边类型白名单 + 布局算法」投影生成。
6. **图谱渲染选型建议**：文档内用 Mermaid，交互主画布用 Cytoscape.js，印刷导出用 Graphviz；>2000 节点启用聚合折叠。

**待用户确认的开放项**（尚未拍板）：交付形态（CLI / IDE 插件 / Web / Agent Skill）、是否允许代码上传云端 LLM、首期支持的技术栈优先级、产物是否入 Git。

## 同日追加：需求文档升级 v0.1 → v0.2（用户补充三条需求）

**用户补充的输入**

1. **以系统级的项目集合为 agent 工作范围**，把 agent 的工作空间圈定在某个系统内，防止访问到其他项目导致图谱混乱。
2. **以版本管理工具（git）确定梳理版本**，后续按版本做增量更新；增量时根据版本变更内容做图谱排查，不必每次全量跑。
3. **交付形态确认：CLI + Web**。

**产出的文档改动**

- `docs/需求文档-系统图谱梳理工具.md` 重写为 v0.2，1320 行。新增一等概念「**系统（System）**」与「**范围守卫（Scope Guard）**」；新增「**版本基线 + 增量更新**」机制；交付形态确认 CLI + Web 双端。
- 亮点章节：§3.2 两条贯穿全局的主线（边界主线 + 版本主线）、§9.5 系统边界守卫策略、§9.6 增量更新推导规则、F1 系统圈定与边界管理（FR-1.1～1.17）、F8 版本基线与增量更新（FR-8.1～8.26）。

**本次确立的关键设计（写入文档，重要）**

1. **边界三层防御**：L1 路径层（硬边界，白名单外直接拒绝并审计）/ L2 依赖层（软边界，系统外依赖建 `external` 节点不展开）/ L3 产物层（组装时校验所有 `source.file` 必须在白名单内，越界即缺陷）。
2. **边界节点语义**：第三方公共包（npm/Maven）**不建节点**（视为平台能力，避免噪声）；外部系统/共享库/共享 DB 建 `external` 节点，新增边类型 `leaves-system`；共享数据库表标记为隐式耦合风险。
3. **扩边必须显式**：系统永不隐式纳入新项目，扩边留痕（`scopeHistory`）并触发影响分析。
4. **增量推导链条**：版本基线 → `git diff --name-status --find-renames` → 按 `source.file` 反查节点 → 沿边按类型扩散（`http-call`/`exposes`/`maps-to`/`reads`/`writes` 跨项目重校验）→ 得出 `mustRerun[]` 与 `skipModules[]` → 合并回图谱并清理悬空边 → 推进基线。
5. **强制全量的信号**：依赖清单实质变更、新增/删除项目、顶层目录重构、路由注册方式变更、抽样校验发现增量与全量不一致。
6. **降级路径**：非 Git 项目退回文件哈希基线，需明示精度下降。
7. **增量硬指标**：增量结果必须语义等价于全量（AC-18）；增量耗时 ≤ 全量的 20%；未受影响模块的 `confirmed` 状态必须保留。

**契约变更**

- 新增 `docs/schemas/system.schema.json`（系统声明 + 边界白名单 + 版本基线 + 边界节点 + 扩边历史 + 审计摘要）
- 新增 `docs/schemas/changeset.schema.json`（变更集：changedFiles / directlyAffectedNodes / impactRadius / skipModules / fullRerunRequired）
- `graph.schema.json`：`workspaceId` → `systemId`，新增 `graphVersion` 与 `basedOn`（版本基线快照），边类型新增 `leaves-system`
- `link.schema.json`：新增 `basedOn`（含 `fileHashes`，供增量判断是否需重跑），边类型新增 `leaves-system`
- **删除** `workspace.schema.json`（被 `system.schema.json` 取代，术语收敛为「系统」）

**验收标准新增**：AC-11～AC-19（边界阻断、边界节点、版本基线、增量正确性、契约重校验、DDL 变更、结构变更升级、增量等价、基线降级），原 11.2/11.3 的编号顺延为 AC-20～AC-25。

**里程碑调整**：新增 M0（系统圈定与边界），M4 拆为 M4（全维度）与 M5（版本增量），M6 为能力外溢。

**用户仍待确认**：LLM 云端/本地、渲染引擎、首期技术栈、`.codeatlas/` 落点（多项目是否同仓）、增量触发方式（手动/hook/定时）、公共依赖白名单规则。用户明确表示「其它的问题我再想想」。
