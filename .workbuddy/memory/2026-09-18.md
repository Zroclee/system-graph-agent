## 第二轮：Q9–Q12 答复与技术选型讨论（尚未回填文档）

**用户答复**：
- **Q9** 目标系统（前后端项目）放在**同一个 Git 仓**；`docs/` 与工具同仓库
- **Q10** Web 画布 → **AntV G6**
- **Q12** LLM 走**本地直连 API**；开发阶段用 **OpenAI + API Key** 快速接入，内网适配后续再议
- **Q11** 语言定 TS；前端 **Vue3 + Vite** 已定；CLI 实现（bun vs express）与是否接 **LangChain** 待讨论

**Q9 结论的影响**：
- 原 Q9 的核心不确定性消解 —— **不需要**"独立载体目录 + 各仓引用"的复杂方案。最简形态成立：**一个系统 = 一个 Git 仓 = 仓根一个 `.codeatlas/`**，版本基线 = 该仓 commit SHA
- **待澄清**：工具仓库（`system-graph-agent`）与目标系统仓库应分开。工具是通用产品（要发版/给别人用），目标系统是私有数据；且工具仓库的 `.gitignore` 已忽略 `.codeatlas/`，自相矛盾
- **修正自己埋的坑**：`.codeatlas/` 下 `facts/` 需入 Git、`index.db` 不入；新增的 API Key **绝不能放在 `.codeatlas/` 内**，应走环境变量或 `~/.codeatlas/credentials.json`（仓库外）。需加 `.codeatlas/.gitignore`

**Q11 讨论结论（我给出、用户未最终拍板）**：
- **纠正概念错位**：Bun 是运行时（对标 Node），Express 是 HTTP 框架（对标 Hono），**不同层**；且 **CLI 不需要 HTTP 框架**（进程内程序，不处理网络）。真正是三个独立决策：运行时 / CLI 参数解析 / Web 服务框架
- 运行时：倾向 **Bun**（TS 直跑、`bun:sqlite` 免原生编译、内置 test、启动快），但 **M0 第一件事必须验证 `web-tree-sitter` WASM 在 Bun 上能否跑通**（go/no-go）；跑不通则退回 Node 22 LTS，此时切换成本 ≈ 0
- CLI：保持 `clipanion`；Web 服务：**Hono 优于 Express**（TS 类型推导、多运行时）
- **LangChain：明确不接**。四条理由：① 理念冲突（它面向自主编排，本项目 D-01 是确定性流水线 + 受控智能）② 能力错配（我们需要的 prompt 边界/schema 校验/强制 fallback/token 预算/缓存键它都不直接提供）③ 依赖风险（迭代快、破坏性变更多）④ 可观测性反噬（tracing 默认有上报通路，与出境审计冲突）
- 唯一备选：Vercel AI SDK `generateObject(zodSchema)`——v1 不接，但在 Provider 实现里留位

**Q12 落地推论**：
- `LlmProvider` 接口是**必需项而非可选项**（内网适配是既定路线）；首个实现 `OpenAiCompatProvider`，内网网关若提供 OpenAI 兼容协议则只需换 baseURL
- **Key 边界**：浏览器（画布）绝不持有 Key → 必须经本地 Hono 服务中转；LLM 调用只发生在 pipeline / 本地服务进程
- **"默认关闭" 从归因手段升级为合规默认姿态**：不接 LLM 时代码完全不出本机
- 出境内容最小化（只发候选片段）+ `audit/` 兼作出境审计
- ⚠️ 开发阶段用 OpenAI 直连时，勿拿生产仓直接跑（真实业务代码会出境）

**当前状态**：Q9/Q10/Q12 已定但**均未回填文档**；Q11 待用户拍板。约定等 Q11 定了**一次性回填** Q9–Q12 + 新增 ADR D-09～D-12 + 更新 §12 技术选型表。

## 第三轮：Q9 更正 —— 系统根是「容器文件夹」，不是 Git 仓

> ⚠️ **本节更正上一节对 Q9 的理解**（上一节按"目标系统一个 Git 仓"解读，错误，保留以存痕）。

**用户澄清（原话要点）**：
- `system-graph-agent`（GitHub）= **工具自身代码的仓库**
- 待拆解的目标系统：**所有项目代码保证在同一个文件夹内**，但**不一定在同一个 Git 仓**
- 用户的追问："`.codeatlas/` 的定义是什么？"

**三个实体必须分清（此前文档从未显式定义，是文档缺口）**：

| 名称 | 是什么 | 归属 |
| --- | --- | --- |
| `system-graph-agent` | 工具自身代码仓 | 我们开发 |
| **系统根（容器文件夹）** | 装着所有待分析项目的文件夹 | 用户提供 |
| **`.codeatlas/`** | 工具在系统根下落的**产物目录**，旁挂元数据，非项目代码 | 工具生成 |

**核查结果：契约层已支持多仓，实现层三处仍是单仓假设**

- ✅ 已支持：`system.schema.json` 的 `versionBaseline.projects[]` 已含 `commit / branch / tag / dirty / fallbackHash / precisionNote`——多仓向量已就位
- ❌ 待改 1：§8.4 `snapshots/<commitSha>.json` —— 单 SHA 命名，需改 `snapshots/<baselineId>.json`
- ❌ 待改 2：SQLite `snapshot` 表 `commit_sha TEXT NOT NULL` + `UNIQUE(system_id, commit_sha)` —— 需改为 `baseline_id` 唯一
- ❌ 待改 3：§9.1 变更集推导第 1 步 `git diff --name-status <from>..<to>` —— 需改为**逐仓 diff 后合并**（git 仓走 commit diff；无 VCS 项目走目录树哈希比对并标降级）

**两处缺失约定（新增）**：
1. **路径基准统一** —— 一切路径（节点 ID / 证据 / changeset / 模块归属）基准为**容器根**，非子仓根。否则两个子项目里的 `src/index.ts` 会互相覆盖，且节点 ID 内容寻址失效。拟立为**不变量 I9**
2. **最近 VCS 根归属原则** —— 判定模块属于哪个 repo：从模块目录向上找最近的、包含它的 VCS 根，保证不出现"同一文件被两个仓认领"

**新发现的一个隐患**：`system.schema.json` 的 `rootDir` 定义为「绝对路径」，但 `.codeatlas/` 位于系统根下（`../` 即可推出系统根），该字段既冗余又导致 **system.json 不可跨机器 / 不可入 Git**（换目录即失效）。建议删除或改为可选覆盖项。

**新增待确认**：
- **Q13** 容器文件夹自身是否初始化一个轻量 Git 仓（只跟踪 `.codeatlas/`，子项目目录全 ignore）？方案 A 推荐：`.gitignore` 写 `/*` + `!.codeatlas/`，自动适配新增项目
- **Q14** 子仓存在未提交改动（`dirty: true`）时的默认行为：拒绝运行（需 `--allow-dirty`）还是一律降级记录？

**待用户拍板（本轮结束时）**：Q9 是否按"系统根 = 容器文件夹"定稿 + Q13/Q14 + 上轮遗留的 Bun/LangChain 两条。

## 第四轮：Q13 撤回 —— 输入侧变更信号 ≠ 产物侧版本管理

**用户确认与纠正**：
1. `.codeatlas/` = **分析系统项目代码时生成产物的保存位置** —— ✅ 用户理解正确，与我一致
2. ⚠️ **Q13 撤回**：用户要的 Git 是**输入侧**——"通过对方使用的版本管理工具找到增量更新的代码，做针对性拆解"；**不是**对 `.codeatlas/` 产物做版本管理。用户明确："这部分有偏差的话先去掉吧，后面再考虑这个功能"

**我的偏差定性**：我把两件事混成一件——
- **输入侧**（用户要的）：Git 作为**变更传感器**。VCS → changeset → 受影响模块 → 定向重跑。**这与 §9.1 / F8 原有设计一致，我并未理解错这一层**
- **产物侧**（我加戏的）：Git 作为**存储层**，把容器根初始化成 Git 仓管理 `.codeatlas/`。**撤回**

**判定**：Q13 **撤销**，移入"后续再考虑"。Q14（dirty 处理）随之降级为 M3 事项。

**撤回后仍需保留的三条**（理由：来自"各项目不同仓"这个用户约束，与产物 git 无关）：
1. §8.4 `snapshots/<commitSha>.json` → `<baselineId>.json`
2. SQLite `snapshot` 表 `commit_sha` → `baseline_id`
3. §9.1 第 1 步 → 逐仓 diff 后合并
→ 均归 **M3 增量里程碑**，可延后实现

**用户措辞点出的新设计点**："对方使用的项目管理工具" —— 说明 VCS 不止 Git。§12 现在写死 `simple-git`，应泛化为 **`VcsAdapter` 接口**（Git 首个实现，无 VCS 走文件哈希降级）。
