**Q1 的答复（已写入文档 §2 §6）**：
- 判定准则（可复用）：**代码能"证明"的绝不给 LLM；只能"猜"的给 LLM 但限定候选集内；都不行的交给人**。三级判定 = 字面证明 → 规则推导 → 语义判断 → 人工清单
- 定性结论：9 个阶段中只有 **S3 链路梳理** 与 **S4 人工确认** 含 LLM 触点
- LLM 任务定为 **6 个**：L1 契约语义对齐 / L2 动态路由解释 / L3 动态 SQL 解释 / L4 模块业务摘要 / L5 链路业务说明 / L6 技术栈兜底判定
- 关键设计：`LlmTask` 接口的 **fallback 为必填字段**（编译期强制）；**默认关闭 + 逐项开关 + 调用留痕**，以支持"效果归因"
- L4/L5 输入**不传源码**，只传结构化事实（API 路径 + 表名 + 符号名）——省 token 且比"让模型读代码猜业务"更准

**文档核心章节**：
- §1 六条设计目标 G1–G6 + 八条不变量 I1–I8（每条都给了违反后果与保障机制）
- §3 monorepo 10 个包 + 依赖规则矩阵（core 为唯一最内层；中间层互不依赖，靠依赖倒置让 pipeline 注入模板实例）+ dependency-cruiser 规则
- §4 zod 为 Schema 单一真源；**节点 ID 内容寻址规范 + 路径规范化算法**（把跨项目契约匹配从"模糊匹配"降级为"ID 相等判断"，是抢回 LLM 活的关键一手）
- §5 S0–S7 阶段契约（输入/输出/执行者/重跑粒度/幂等/失败模式）
- §7 **四道闸门 + 证据回验**：伪造一条证据需同时满足「路径在白名单内且存在」「行号窗口命中」「片段逐字一致」三重条件
- §8 JSON 事实源 + SQLite 派生索引，给出约 15 张表的完整 DDL
- §9 增量失效：变更集推导 → 跨项目影响扩散（BFS 三类反向索引）→ 模块指纹 → 保守升级规则
- §14 ADR 决策记录 D-01～D-08 + 风险 R1–R8 + 待确认 Q9–Q12

**两个我在文档里特意点出的隐蔽陷阱**：
1. **缓存键必须含「依赖契约面哈希」**（I7）——只按自身源码哈希会漏掉"后端改 API 签名、前端未动"的跨项目失效，导致图谱看着完整但内容过期
